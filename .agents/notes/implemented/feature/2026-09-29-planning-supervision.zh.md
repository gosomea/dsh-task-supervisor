# Agent Note: 规划监督、截断恢复与可选执行批准

Status: implemented

[English](2026-09-29-planning-supervision.md) | 简体中文

## Problem

受督导任务可能在提交计划前耗尽单次生成额度。此前监督等待正式提交，任务可能停在空闲状态，缺少有证据支持的下一项产出。审查者也可能在记录决定前达到生成上限。截断不能证明任务成功，也不是用户决定。

[前七个评测位置分析](../../../../eval/deepswe/results-20260929-7/analysis.zh.md)记录了没有提交计划的原生 max-tokens 结束。冻结评测保持原样。这些现象支持补齐恢复和规划监督，但不能证明它们提高独立奖励。

## Decision

同一插件控制器负责续行和批准。原生 Session 事件仍是事实来源，独立审查者通过持久化结构化决定提出建议。插件不修改原生 Goal/Plan 或沙箱。[验收记录](../../../../docs/planning-supervision-validation.zh.md)区分原生 loop 回归、明确降低上限的真实模型探针和日常配置验收。

### 默认设置与任务控制

| 设置 | 默认 | 行为 |
| --- | --- | --- |
| `truncationRecovery` | `true` | 在原生步骤和队列结清后恢复获准运行的主模型生成。 |
| `maxRecoveryWithoutProgress` | `2` | 重复恢复没有新增可验证工具产出时暂停。 |
| `planningSupervision` | `true` | 在正式提交前观察勘察与计划形成。 |
| `maxPlanningWithoutProgress` | `2` | 重复观察没有新增相关事实或解决未知项时暂停。 |
| `executionApproval` | `manual` | `after-review` 预授权当前任务在正式计划审查通过后首次执行。 |
| `reviewRepairAttempts` | `1` | 限制同一审查 Session 的协议补交次数，包括已结清的审查截断。 |

profile 偏好在每个任务创建时记录。首次批准前，可用 `/task auto-approve-on`、`/task auto-approve-off`、侧栏按钮或明确的督导对话指令修改持久策略。普通问询不授予批准。界面展示有效策略及来源。审查进行中仍可撤销，待应用的控制结论随即失效。

`automaticContinuation: false` 阻止自动开启下一轮，包括主模型截断恢复。可以记录策略批准，但不会自动开启执行轮次，仍需用户明确恢复。暂停、关闭、重启和 fork 不会静默恢复。

### 主模型生成恢复

恢复要求最新实际原生请求以 max-tokens 结束，步骤和工具义务结清、没有后续活动、inbox 为空、当前任务获准继续且身份和版本不变。同一轮保留的早先 max-tokens 标记不能覆盖后来的成功请求。取消、错误、阻塞和中断各自处理。

控制器保存原回合、截止点、产出指纹、次数、精确输入 ID 和带上下文的续行正文；先 flush，再核对身份、状态和队列后交付。失败时在原生维护任务释放驱动器前撤回该输入。重复回调不产生另一条恢复。重启重建状态并等待手动恢复。

续行明确目标、已确认工具事实或已通过节点、证据引用、缺少的产出和当前执行权限。不把推理当作已执行工作、不重放效果未知的调用，也不把 Token 增长或重复错误当作进展。

### 计划形成期间监督

规划审查在 DAG 形成前读取主 Session 原始证据，区分有支持的事实、未知项和下一项具体产出。通过只允许继续规划，修订用于纠偏，需要用户决定则暂停。即使审查者声称有进展，重复相同事实也不能重置停滞计数。

观察复用现有阈值：24 条工具结果、有已完成工具活动且经过 5 分钟，或连续 3 次工具错误，在下一次 pre-step 检查。未提交计划的正常轮次结束和再次截断可提前触发。这些阈值只请求审查，不能证明跑偏。纯长生成只在支持的原生边界交付干预。

新用户输入、暂停、关闭或任务变化使待应用控制结论失效，发现作为历史证据保留。内部故障保持审查故障，不能变成用户拒绝或自动通过。规划审查不能替代正式计划覆盖审查。

### 可选执行预授权

自动批准要求同一主 Session、任务和要求版本的持久授权，有效的结构、来源与依赖，以及精确关联的正式计划审查通过。即使 `planCoverageReview: false` 也强制覆盖审查。修订、需要用户决定、协议故障或超时均不批准。获批计划必须匹配审查输入，不能只匹配标题或结论。

批准记录 source=policy、授权 seq、计划版本及审查作业 ID。控制器不伪造用户消息，`task_approve` 保持直接用户批准校验。手动与策略动作竞争时只准入一次执行。编辑要求清除原批准和预授权。旧记录与 fork 后的 Session 不能授予该权限。

完成后修复仍展示受影响 DAG 节点，每次等待用户点击确认。自动批准不扩大文件、网络、沙箱或发布权限。

### 审查截断补交

已结清的最新原生审查 max-tokens 结束可进入现有有限协议补交路径。补交保持同一 Session、任务修订、截止点、快照、已读证据和原截止时间，要求基于现有证据提交结构化决定；证据不足仍须修订或请求用户决定。耗尽后暂停并保留原 Session 和错误序号。

### 持久化与展示

任务记录版本 14 和投影版本 15 准入执行策略，审查记录版本 3 准入规划决定。读取器接受旧记录，但不补造新授权。主 Agent 回答保持原生；简略督导发现和任务进度连接侧栏证据与批准策略详情。

## Alternatives considered

**只提高生成上限。** 更高上限能减少部分截断，但不能替代恢复。

**每次空闲都继续。** 这会忽略批准、暂停和未确认工具效果。

**只审已提交计划。** 这会漏掉计划形成期间的停滞。

**让审查者指挥执行。** 这会产生第二个续行所有者。

**自动批准所有任务。** 手动批准保持默认，因为自动执行需要明确预授权。

## Consequences

三个顺序批次交付恢复、规划监督和预授权执行，不改写冻结评测结果。原生 loop 与真实模型证据由[验收记录](../../../../docs/planning-supervision-validation.zh.md)维护，降低上限的探针不能证明日常配置成功。当前日常 CodeBuddy 使用 maxTokens=32000 和 provider 默认推理，早先 8192 探针明确属于测试上限。

额外审查和续行增加耗时与 Token，这些阈值不是已测得的最优值。摘要可能漏掉事实，审查者即使引用有效也可能建议错误；仍需原始证据和独立结果评分。长程提升、纠偏收益和误暂停尚未测量，需新冻结对照和盲审标注。

本文扩展[审查策略](../../../../docs/review-policy.zh.md)与[会话运行时](../../../../docs/session-runtime.zh.md)。相关记录的职责和生命周期仍适用，因此保持有效，不覆写先前历史。
