# 首个原型与 Agent Team 对照

**状态：原型设计，已有可运行的纵向切片。** 本文定义首个原型和作为竞争方案的 Lead–Worker 模式。完整产品及组合对照组尚未运行；[实现状态](implementation.zh.md)记录可运行范围，[内核试验结果](host-spike.zh.md)记录早期发现的持久化缺口。

## 团队方案确实有竞争力

根 Lead 可以规划、用原生 Goal 续行、把实现委派给 Worker、检查结果并要求修正。这能复现不少预期用户体验。本地 [Agent Team 服务](../../../deepseek-harness/packages/experimental/agent-team/README.zh.md)已经有持久消息、版本化任务板和恢复能力；持久化和多 Agent 不是 Supervisor 独有优势。Team、Goal 和 Plan 组合的 preset 能否完整运行，仍需实际组合测试。

原生 Goal 工具从存活根 Agent 的直接用户轮次授权创建和控制任务；完成操作还接受匹配的原生 goal round。子 Agent 不能仅因为看见工具就获得这些权限。原生 Plan 也限制仍被存活父 Agent 拥有的子级打开计划审批。依据见 [Goal 权限实现](../../../deepseek-harness/packages/goal/tool-goal/src/authority.ts)和 [Plan 限制](../../../deepseek-harness/packages/plan/plan-mode/README.zh.md)。根 Lead 可以先规划、获批后执行；同时具备能力不代表规划与执行处于同一阶段。

## Supervisor 必须增加什么

| 关注点 | Lead–Worker 对照 | Supervisor 要求 |
| --- | --- | --- |
| 执行归属 | Lead 委派并协调 Worker。 | 用户的主 Agent 保持自己的执行会话，无需增加一个项目经理 Lead。 |
| 审查时机 | Lead 选择何时检查、何时请求再审。 | 控制层强制执行配置的阶段与兜底检查点，不依赖主 Agent 愿不愿意申请。 |
| 完成判断 | 模型发起任务状态更新，原生 Goal 完成遵循其工具权限。 | 主 Agent 只能申请完成；控制层根据通过的证据才能记为完成。 |
| 证据 | Lead 可检查共享工作区和可用日志，不必只依赖 Worker 总结。 | 审查者有明确的执行日志只读入口，引用证据截止点和任务版本。 |
| 恢复 | Team 已持久保存协作状态，原生 Goal 也有续行规则。 | 一个控制层统一处理编辑、关闭、旧结果拒绝、手动恢复及审查失败恢复。 |
| 模型判断 | Lead 可能判断正确，也可能错误。 | 审查者同样可能判断错误；强制审查不保证审查正确。 |

Supervisor 是带模型评估的任务控制器。控制层拥有状态转换和调度，主 Agent 拥有实现和计划提议，审查者提供有证据的建议。审查者不能成为第二个实现者、创建实施 Worker、静默改写用户目标或调度任意工作。内部可以使用 DSH 子 Agent 提供方运行审查，而产品无需变成团队管理界面。

这个区分是工程约定，不意味着 Team 永远不能实现同样行为。如果为 Team 加入等价的强制检查点、验收权限和恢复语义，它也获得了相似的督导机制。价值假设是：把这些规则固化成插件，能以更少的用户协调获得更可靠的完成结果。评测必须允许推翻这个假设。

## 原型范围

做完整的一条执行链：一个受督导任务、现有主执行会话、每个检查点一个新的审查作业。这是[有限任务列表设计](task-lifecycle.zh.md)的明确子集。五任务排队、专项审查者、连续审查会话、原生 Goal 或 Plan 导入，以及结合 Team 执行，可在控制循环跑通后增加。fork 保留设计，但不在首轮验收声明范围内；原型不能静默让 fork 开始续行。

用户命令暂定 `/task new`、`/task`、`/task edit`、`/task pause`、`/task resume`、`/task clear`、`/task off`，加上面板中的重新启用动作。首次计划批准覆盖进入自主执行。单独的仅规划命令作为后续 UI 扩展；原型仍会生成并记录初始计划。

| 组件 | 最小交付 |
| --- | --- |
| 任务状态 | 持久目标、约束、验收标准、计划阶段、版本、状态、证据截止点和可恢复的 JSON 快照。 |
| 主 Agent 工具 | 独立的任务状态读取、计划提交、阶段汇报和完成申请操作；确切名称与 schema 在宿主验证后确定。 |
| 审查输入 | 当前任务与计划、限定范围的主会话日志、产物引用，以及可分页展开的原始证据。 |
| 审查输出 | 匹配的任务版本和证据截止点、有依据的发现，以及通过、修订或需要用户输入的建议。 |
| 续行 | 用户输入和必要审查处理完成后，准入一个经过版本检查的下一步。 |
| 独立验收 | 在包含实际任务修改的隔离快照上运行受控 fixture 的验收检查。 |
| 右侧面板 | 目标、当前阶段、执行状态、带证据的最近发现、下一步、计划批准、暂停、恢复和关闭 Supervisor。 |

## 已确认的原型细节

以下选择作为原型方案采用。每项机制仍需宿主验证，不能在失败场景验证前将规则写成已被强制执行。重试与停滞次数仍是待校准的可配置默认值。

| 细节 | 原型规则 | 所需证据 |
| --- | --- | --- |
| 首次批准之前 | 允许仓库查看与计划提交；批准前的工作区修改、任意 shell 执行和委派须由宿主限制，只有提示词不够。 | 未批准的修改被拒绝，查看和计划提交正常。 |
| 任务要求 | 约束与验收标准使用稳定 ID；批准绑定提交的计划与要求版本；阶段关联标准，模型不能静默删掉标准。 | 计划修订保留标准，或引用用户修改该标准的指令。 |
| 阶段汇报 | 提交阶段 ID、关联标准、产物或测试证据引用和剩余工作；汇报在审查前只是提议，阶段数量不作进展分数。 | 缺少必要证据的阶段仍保持未完成。 |
| 新用户输入 | 先使排队准入和旧审查权限失效，再处理新输入；普通询问不能自动改写为新目标。 | 用户编辑优先于旧审查，状态询问不会创建新任务。 |
| 续行交付 | 使用进入日志的 Supervisor 消息来源，不伪装成直接用户输入；单纯被动注入上下文不能唤醒空闲 DSH Agent。 | 到期续行只唤醒一次，关闭能在准入前使其失效。 |
| 审查者生命周期 | 监听绑定被督导主 Agent 身份，排除审查和验收作业；同一任务版本与证据截止点只开一次审查。 | 审查者调用工具不会再触发另一次审查。 |
| 审查失败 | 同时要求正常结束与输出 schema 有效；暂时性调用失败暂定最多两次有界重试，之后暂停并说明恢复原因。 | 超时、格式错误和模型调用失败都不能成为通过结论。 |
| 产物稳定性 | 最终快照前等待自有作业结束；fixture 只用有界前台进程，不使用脱离管理的后台工作；验收前固定代码与相关数据快照。 | 相关文件变化或自有写入作业仍活跃时，不复用验收结果。 |
| 可见状态 | 展示规划中、待批准、执行中、审查中、已暂停、正在停止或已结束，并附原因；关闭面板不等于关闭督导。 | UI 与回放状态能说明当前为什么没有继续执行。 |

首个审查者在新会话中默认跟随主 Agent 的有效模型选择，也允许用户从当前 DSH profile 配置的模型中指定；选择时点、重试固定路由与配置边界见[审查模型](review-model.zh.md)。证据访问仍限定于绑定任务和主会话前缀。宿主无法提供的 token 用量标记为不可用，不记作零。

## 阶段证据与纠偏

阶段提议包括目标、关联验收标准 ID、预期可观察产物或检查，以及前置条件。主 Agent 自行拆分阶段。阶段可以拆分或合并，但获批标准始终能够追溯。证据保存原始事件与产物引用；总结里写“测试通过”不是测试结果。

纠偏审查指出未满足的标准、支持证据，以及下一步需要补充的事实或修复。对于同一项已覆盖行为，通过的可执行检查优先于没有依据的相反模型判断；未被测试覆盖的更广要求仍需证据。审查分歧必须指向具体剩余要求，不能只是风格偏好。暂定同一问题经过两次纠偏续行仍无新证据时，触发停滞判断并手动暂停。这统计失败的纠偏循环，不统计重复工具名称，后续仍需校准。

## 首个服务 fixture

旧网站演示退出原型及其验收路径。创建一份可复现的小型 Python 与 SQLite 服务种子，已有正常的单条记录创建和读取行为，再要求主 Agent 增加批量导入。这是合成开发 fixture，不是已经选定的真实仓库，也不代表长程能力证据。

| 公开验收标准 | 外部验证 |
| --- | --- |
| 有效批次成功持久化，并通过服务接口返回。 | 提交批次，检查响应，再读取已保存记录。 |
| 非法输入使整批被拒绝，不能部分写入。 | 在批次中间放一条非法记录，对比前后数据库状态。 |
| 同一请求键重试不重复写入，同键不同内容被拒绝。 | 重放请求，再提交冲突内容，检查记录数量和响应语义。 |
| 现有单条记录操作保持已约定行为。 | 对种子公共接口运行回归检查。 |

构造 fixture 时固定确切请求与响应语义。向主 Agent 和 Supervisor 提供公开要求及有代表性的可运行检查；最终评分保留另一套外部测试，但不得隐藏额外要求。每组都恢复同一份 fixture。验收脚本和参考结果维护在候选工作区之外；执行前先固定候选代码与相关数据库产物快照。

## 技术试验与实现条件

首个技术试验必须证明三项宿主能力：独立命令和模型工具组合；在受支持的检查点暂停并恢复主 Agent，同时由独立审查者读取它的日志；状态持久化并在重启后保持停用续行。还要覆盖审查进行中关闭。源码存在某个钩子或类型，不代表组合后的流程已经能无重入、无死锁地工作。

如果缺少必要宿主能力，记录确切缺失操作，再判断是否值得做最小 DSH 扩展。不能为了演示成功，静默把 Supervisor 变成对话式 Lead、运行未被记录的独立续行循环，或放宽验收要求。上述能力验证后，再实现 fixture 执行循环和最小面板；队列、专项审查者和完整基准后续再做。

## 端到端演示

使用上述批量导入服务 fixture，覆盖校验、持久化和 API 响应的修改，并保持现有行为。允许主 Agent 自行制定计划。fixture 提供公开验收要求和独立评测检查，不提供只有 Supervisor 能看到的指定计划。

演示必须展示：由 `/task new` 创建任务、一次计划批准、真实实现、有证据的审查、至少一次获准续行，以及经过独立检查的完成。另行受控运行覆盖遗漏要求、用户编辑后旧审查迟到，以及待处理工作期间关闭或重启。可以用注入输出测试控制正确性，但必须标明；演示模型审查质量时必须使用真实审查输出。

主 Agent 结束回复却未提交阶段汇报，不等于任务完成。控制层核对状态，并在到期时请求检查点。审查失败不能算通过。工具正常退出本身不能替代任务验收标准。

## 实现顺序与验收

1. 验证专用 preset 能组合任务命令、模型工具、日志读取和右侧面板，且不要求 Goal、Plan 或 Team 服务；验证宿主支持的空闲续行与取消边界。
2. 实现以事件为依据的任务状态、快照、编辑和关闭处理；接模型前先用确定性测试检查重复准入、过期结果、重启和取消。
3. 将主 Agent 的计划与进展操作接入具有受限日志读取能力的新审查者；模型可见指令保留在会话记录中。
4. 通过实际 DSH 模型调用与隔离验收跑通完整 fixture；确认手动恢复和关闭 Supervisor 后不再产生自有工作。
5. 同一个 fixture 跑最强的实用 Lead–Worker 对照，再扩展 UI 或任务容量。

原型验收要求完整循环和可靠停止，不要求已经证明基准优势。阶段检查场景须拒绝无依据的完成申请，并在修正产物后接受完成。编辑场景须拒绝旧审查决策；关闭场景须拒绝迟到的续行和超时回调；重启场景须保留状态，并在手动恢复前保持空闲。

## 与团队比较

增加根 Lead 加一个 Worker 的必要产品对照，Lead 上使用原生规划和 Goal 续行。明确要求 Lead 验证工作并纠错，向它提供等价的任务要求、工作区产物和执行证据访问。先验证组合 preset 和真实任务控制权限，不刻意用只能看到总结或没有审查指令的 Lead 制造弱对照。

使用相同主模型、任务 fixture、权限和预先声明的执行上限，记录全部 Lead、Worker 和审查者消耗。审查者使用更强模型时，为 Team 组匹配这项资源，或作为独立的模型分配实验报告。统计用户决策次数、无依据的完成、纠偏、不必要额外工作和最终独立验收。如果 Team 以更简单的配置达到相同效果，应收窄产品结论或复用该机制，不能预设插件更优。

## Dev Note

fixture 约定需要可执行测试；确切工具 schema、宿主检查点传输和 Team 对照组合仍需实现证据。原型限制一个活跃任务，完整设计仍默认五个未结束任务。两项数量限制都不证明性能优势。
