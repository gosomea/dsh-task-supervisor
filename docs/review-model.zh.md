# 审查模型选择

**状态：已确认的产品方向与待实现细节。** 审查默认跟随主 Agent 的模型选择；用户也可从当前 DSH profile 配置的 provider 与模型中指定审查模型。本文负责选择、配置生效时点和恢复记录，任务恢复见[督导会话](session-runtime.zh.md)。

## 选择入口

右侧 Supervisor 设置提供“跟随主 Agent”和“指定模型”两种策略，默认前者。“指定模型”复用 DSH 的 provider 分组、模型目录和该模型支持的推理档位。Supervisor 保存选择策略及必要的 provider、model、reasoningEffort ID，不另建 API key、base URL、模型账号或模型名称注册表。

默认策略属于 Supervisor 在当前 DSH profile 中的插件设置，通过 DSH 配置编辑机制保存。第一版不增加每个任务各自的模型覆盖，以减少恢复优先级。该设置不修改主 Agent 的当前模型，也不改变 DSH 全局默认模型；模型本身的 provider、凭证和调用仍由 DSH 管理。

## 已核实的 DSH 行为

| 入口 | 已有行为 | 集成约束 |
| --- | --- | --- |
| [agent-default-model](../../../deepseek-harness/packages/core/agent-default-model/src/index.ts) | 持有 profile 配置中的默认 provider、model 和推理选择。 | 默认值不能覆盖已有的会话选择。 |
| [Session 模型选择](../../../deepseek-harness/packages/api/session-controller/src/model-selection-projection.ts) | 区分 pending 选择和最后使用的请求模型。 | 刚切换但尚未请求的模型也必须被“跟随”策略看到。 |
| [子 Agent 默认继承](../../../deepseek-harness/packages/subagent/subagent/src/child-agent.ts) | 优先使用主会话最近请求头，首个请求前回退到创建选项。 | 实验确认它不会单独读取待生效的 `model/selection`；不能把省略覆盖等同于跟随当前选择。 |
| [原生模型选择 UI](../../../deepseek-harness/packages/client/ui-model-selection/README.md) | 共享 provider 分组与模型目录，使用模型实际支持的推理档位；目录是建议列表，路由另行验证。 | 复用目录与选择组件，不复制模型列表；目录缺项不自动证明现有路由不可用。 |
| [Session 选择命令](../../../deepseek-harness/packages/api/session-controller/src/commands.ts) | 会修改会话模型，并尝试保存 DSH 默认选择。 | 审查模型设置不能直接调用这一写入口，否则会连带改变主模型或默认值。 |

## 跟随策略的解析

每个新审查作业在分派之前解析一次主 Agent 的有效选择。优先使用宿主提供的会话选择读取能力，语义为待生效的用户选择优先于最近请求模型；尚无会话选择或请求时，尊重该 Agent 的显式创建路由，再使用宿主默认选择。推理档位的省略保留“使用模型默认”的含义，不能把旧模型的档位带到另一模型。

目前 pending/lastUsed 的完整折叠在 API Session Controller，而子 Agent 的公开继承函数读取最后请求头。首版应验证一个宿主无关的公共有效选择读取入口，必要时将现有折叠抽到通用模型选择模块；不读取 Web Controller 私有对象，不复制一套长期维护的模型选择状态机。该公共入口仍是待验证集成项。

解析后通过 DSH LLM 服务校验 provider、model 和推理设置，把具体结果作为审查作业的显式 Agent 配置。这样既能复用 DSH 路由，也能避免分派期间主模型变化导致审查配置不明确。主 Agent 的工具权限、可写工具和全部上下文不会随模型选择一同复制；审查者仍使用受限证据工具。

## 生效时点

| 场景 | 规则 |
| --- | --- |
| 新审查作业，策略为跟随 | 捕获分派时主 Agent 的有效模型选择。 |
| 新审查作业，策略为指定 | 解析当前 Supervisor profile 设置中的固定路由。 |
| 主 Agent 或 Supervisor 设置在审查中改变 | 当前审查保持已捕获路由；下一项新审查采用新选择。 |
| 同一作业的暂时性失败重试 | 默认固定原路由与推理设置，记录新的 attempt ID；不静默换模型。 |
| 用户明确要求用新模型重审 | 取消或作废旧作业，创建新作业；沿用任务与证据版本核对。 |
| 重启后已有完整审查结果 | 复用记录用于恢复核对，不调用当前模型改写旧结果。 |
| 重启后作业中断 | 手动恢复后核对旧尝试；续试保留已记录路由，重新发起的审查按当前策略解析并记录新身份。 |
| 模型不可路由、凭证缺失或推理配置无效 | 显示具体错误，必要审查保持未决；不自动改为跟随、不换 provider、不视为通过。 |

改变模型选择本身不改写任务目标或已批准标准。不同模型得出的新结果同样需要任务版本、证据截止点和产物身份检查。默认独立验收中的模型判断也使用本策略；固定测试命令无需模型选择。

## 持久记录

每次审查记录策略种类、策略修订、选择来源、解析时的主会话证据游标、具体 provider/model/推理设置、作业与尝试身份，以及实际子会话请求头引用。用户请求的配置与适配器实际采用的配置分开保留。模型显示名称只用于 UI，不能作为稳定身份；profile 名称只是本地配置来源，不能单独证明环境可复现。

不保存凭证值。token 用量按实际返回记录，缺失记为不可用。同一个模型 ID 可能由 provider 更新服务版本，因此记录可用的 provider 版本或响应元数据，同时避免宣称仅凭模型名即可逐位重放。

## 验收

验收覆盖：主会话已请求后的继承、首次请求前的默认选择、已切换但未请求的 pending 模型、固定模型、推理档位变化、profile 配置变化、审查中切换、重试固定路由、重启恢复，以及无效路由明确失败。设置审查模型后，断言主 Agent 和全局默认值没有被修改。

受控对照评测仍记录各组实际模型配置。若用户给审查者指定更强模型，Team 对照也应匹配资源，或单列为模型分配实验；该产品配置能力不改变[评测设计](evaluation.zh.md)的比较规则。
