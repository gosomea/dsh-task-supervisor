# 督导会话与恢复设计

**状态：调研后的设计建议，尚未实现。** 本文负责持久记录、恢复权限、动作交付、日志读取和故障验收；任务含义见[任务生命周期](task-lifecycle.zh.md)，实测范围见[内核试验](host-spike.zh.md)。建议把这些职责放在同仓库的 `supervisor-session` 模块中，暂用包名 `dsh-supervisor-session`，由完整插件统一安装；暂不另建仓库或发布第二个产品。

## 建议结构

引入 **Supervisor Session（督导会话）**：一个可回放的任务控制记录，以及它与主执行、审查、验收会话的绑定。它提供恢复服务和统一审计视图。主会话的原始消息、工具结果和督导控制记录继续由同一条 DSH Session 日志承载；审查者各自保留原生会话日志，主日志保存关联引用。`supervisor.json` 和统一时间线都是可重建投影。

“Super session log”可作为这个联合视图的直观叫法。持久化设计不复制一份主 Agent 全量日志，不另设需要与 DSH 双写同步的权威任务文件。逻辑上的完整视图可以由多条有明确关联的原生日志组成。

| 层 | 拥有的职责 |
| --- | --- |
| DSH Session 与 persistence | 事件顺序、单写入者、物理日志、持久化屏障、损坏检测及格式迁移。 |
| 通用宿主扩展能力 | 外部插件记录的可读格式；受控会话在控制器缺失或不兼容时的执行准入。此项存在缺口。 |
| `supervisor-session` | 控制记录 schema、确定性回放、状态投影、恢复核对、动作去重、证据引用和有界读取。 |
| `dsh-task-supervisor` | 规划、审查策略、下一步选择、完成裁决和用户界面。 |

## 源码与实验确认的事实

| 事实 | 对设计的影响 |
| --- | --- |
| [SessionPersistence](../../../deepseek-harness/packages/session/session-persistence/src/index.ts)已提供读句柄、排他写句柄和 `flush()`。 | 复用其所有权与持久性约定，不再自建日志锁和写入器。 |
| `append` 的通用约定不保证崩溃持久；`flush` 才是屏障。 | 控制动作对用户确认或触发后续工作前，要等屏障成功。 |
| [Session.append](../../../deepseek-harness/packages/core/session/src/index.ts)未提供外部事件兼容标记；未知必需事件在重读时被拒绝。 | 纯类型声明不足以接入。上一轮复现仍然成立。 |
| [`ignorable` 的约定](../../../deepseek-harness/packages/core/session/src/types.ts)仅适用于省略后不影响重建的信息记录。 | 影响批准、关闭、完成与续行的记录不能直接标为可忽略。 |
| `runMaintenance()` 在空闲阶段独占执行；实验已验证其中排入的 followup 在 `flush()` 后释放才开始请求。 | 空闲续行可复用此入口实现先持久后执行，不需要另造一个唤醒循环。 |
| 原生恢复保留待处理 inbox；实验中，后续普通用户消息会唤醒旧督导消息。 | 恢复时必须撤销旧许可，并通过公开 inbox API 移除或隔离自有旧消息。 |
| `agent/created` 初始化可在运行前执行；实验已验证只移除旧督导消息并保留用户输入。 | 可作为控制器存在时的恢复入口；不能证明控制器缺失时也会拦截。 |
| [中断修复](../../../deepseek-harness/packages/core/session/src/repair.ts)区分未开始工具与 `TOOL_OUTCOME_UNKNOWN`。 | 原生补齐轮次边界不代表业务动作成功；有副作用的未知结果须核对。 |
| [storage-domain](../../../deepseek-harness/packages/storage/storage-domain/README.md)提供持久 KV，但不把变更放进 Session 日志。 | 适合派生索引与缓存，不能直接替代任务控制事件。 |

## 备选方案

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 只保存一份任务 JSON | 实现直接，当前状态易读。 | 缺少批准、动作和审查历史，难以判断崩溃窗口；不采用为权威历史。 |
| 复制所有消息到新的 super log | 可自行定义格式。 | 增加双写、缺口修复、fork、删除、迁移和隐私副本；首版不采用。 |
| 独立的督导控制 journal，原生日志仅作证据 | 可避开未知 Session 事件问题。 | 是有效备选，但须处理两份存储间的交付与回执；仍不能独自阻止控制器缺失后的宿主执行。 |
| 替换整个 SessionPersistence provider | 可完全控制存储。 | 要兼容现有 Session、迁移、SDK、导出与核心校验；范围过大，首版不采用。 |
| 原生事件扩展＋督导恢复模块 | 保留一个有序的主控制历史，复用 DSH 持久化。 | 需要通用宿主扩展；作为推荐路线，先做窄范围可执行验证。 |

采用独立 journal 会改变目前“主 Session 是督导事件权威”的约定，必须明确修订此设计并实现交付协议，不能作为看不见的临时绕路。KV 后端支持 SQLite 也不意味着已获得跨 Session、跨记录的事务；现有 [SQLite provider](../../../deepseek-harness/packages/storage/storage-sqlite/README.md)公开的是单语句 KV 写入原子性。

## 所需宿主扩展

建议探索宿主理解的通用插件记录信封，暂称 `extension/record`，包含命名空间、绑定身份、记录种类、payload 版本、操作身份和显式证据引用。名称与字段是提案，不是已有 API。记录仅进入日志；发给模型的内容仍经正常 inbox 和 `user/message` 记录，不能把不透明 payload 偷渡为模型上下文。

配套的执行要求应由宿主在创建、恢复和下一步准入时检查：绑定的控制器是否存在、是否理解记录版本、恢复是否完成、执行许可是否仍有效。要求必须可从持久记录确定，不能只查询当前已挂载插件名单。只有记录种类已注册而没有缺失语义，不能解决问题。通用准入检查必须在控制器卸载后继续有效。

兼容的新宿主允许只读查看不认识的业务 payload，但执行受控会话前必须取得兼容控制器。缺失时保持只读并说明原因。更旧、完全不认识通用事件类型的 DSH 仍可按现有规则拒绝打开，不承诺降级可读。新机制还须经过存储格式、SDK 投影、导出和相邻迁移规则验证；不能把它描述为仅改一个布尔参数。

`/task off` 停止并保留督导关系，插件正常加载时仍可普通对话；它不等同于卸载恢复模块。解除绑定是单独的显式操作，只能在自有动作收敛、旧队列清理且记录持久化之后进行。解绑不把未完成任务记为成功。首次原型可以不提供解绑命令，但卸载后不能静默以普通执行模式恢复受控工作。

## 记录与身份

| 记录类别 | 最小内容 |
| --- | --- |
| 绑定与版本 | 督导会话 ID、主 Session ID、控制器协议版本、schema 版本与绑定状态。 |
| 任务和计划 | 任务 ID、任务版本、要求与验收标准 ID、计划版本、用户指令引用。 |
| 批准与用户决定 | 决定 ID、批准的要求和计划版本、来源事件；普通提示超时与明确批准分开。 |
| 审查与验收 | 作业 ID、尝试 ID、任务版本、证据截止点、实际模型设置、结果及应用状态。 |
| 动作 | 动作 ID、当前运行世代、目标任务版本、下一步摘要、inbox 消息 ID、开始与结束引用。 |
| 恢复与停止 | 中断原因、已核对事实、撤销的许可、停止状态和等待用户的原因。 |

每次进程恢复或控制器重新挂载，都建立新的运行世代。它隔离旧回调和旧许可；持久日志显示 `active` 不授予新世代继续执行的权限。旧世代结果可保留作证据，但不得直接控制当前执行。

业务事件使用稳定 UUID；DSH 原始证据引用同时包含 Session ID、逻辑格式版本与 seq。不能把裸 seq 当成跨格式迁移的永久地址。迁移若没有可靠引用映射，旧审查结论保留为历史，新执行前重新绑定证据；不能按时间戳或近似文本猜测。跨会话关联依靠显式父子和动作引用，时间戳只用于展示。

回放是确定性折叠：输入已保存记录，得到状态与待核对事项。回放不调用模型、不运行工具，也不重新批准任务。快照保存已应用游标、schema 和所依赖的日志前缀身份；缺失或过期可重建，超前于日志、损坏或版本不支持时不能成为执行依据。控制记录追加失败后禁止“只更新内存继续运行”。

## 动作交付与持久性

1. 在当前主 Session 的单写入所有权下，检查任务版本、运行世代、用户输入和审查状态，生成唯一动作 ID。
2. 追加动作准备记录并等待持久化屏障；尚未持久化时不向用户声称已获准执行。
3. 空闲时通过已验证的 `runMaintenance()` 独占阶段，把带动作 ID、任务版本和世代的消息排入原生 inbox，等待 `flush()`，再复核许可并退出维护阶段。其中的 `followup` 延后到维护结束才运行；不要在维护任务内部等待本 Agent 的 `whenIdle()`。活动轮次仍须使用步骤准入机制。
4. 在最终步骤准入处再次核对许可并持久记录准入；工作区副作用必须发生在有效许可之后。任一等待期间的 edit、pause、off 都使旧许可失效。
5. 通过原生 inbox、请求、工具及轮次事件关联实际执行，记录结果；同一动作的重复交付不能产生第二次有效准入。

控制器使用同一 Session 的写入路径，不另开竞争写句柄。首个试验可用现有服务级 `sessionPersistence.flush()`；它覆盖全部活动写句柄，可能受无关会话失败影响。若后来需要每会话屏障，应扩展公开能力，不访问循环私有句柄。

日志与模型请求、文件修改、网络请求之间没有通用原子事务。保证目标是持久记录已接受的控制决定、抑制重复准入，并显式处理不明结果；不能承诺任意外部副作用恰好发生一次。崩溃后读到已准入但没有结果，必须核对外部状态；只读或已有业务幂等键的动作才适合受控重试。

## 恢复顺序

恢复时先禁止受控执行，再取得原生 Session 写入所有权，完成物理读取和宿主中断修复。验证控制器与 schema 后，回放状态并撤销旧世代许可；用 inbox 中的来源和动作身份核对排队消息，只移除或隔离自有过期消息，保留用户消息。取消需要保留 inbox 时使用宿主的 `keepInbox` 语义，再按消息身份清理，不能用全量 clear 代替自有工作清理。审查者及验收者的旧结果按任务版本和证据截止点核对。

随后记录恢复结论、等待持久化屏障，再显示可操作状态。默认停在“等待手动恢复”；旧超时不会使其自动继续。用户恢复后重新核对工作区、模型路由、待处理用户决定和必要证据，生成新世代动作。初始计划已有批准可以保留，但未解决的必需决定仍阻止执行。

关闭时先在内存中撤销准入并请求取消自有工作，再持久记录停止意图，等待作业收敛及最终屏障。写入失败时仍保持本进程停止，向用户说明停止状态尚未成功持久化；不能返回成功后继续执行。下次启动依旧等待手动恢复。

| 崩溃或故障位置 | 恢复处理 |
| --- | --- |
| 准备记录未持久化 | 不推断动作被接受；按最后有效前缀恢复。 |
| 准备已持久，消息未入队 | 显示未交付，手动恢复后重新决定是否交付。 |
| 消息入队，尚无有效准入 | 撤销旧世代消息；普通用户发言不得使它复活。 |
| 已准入，工具结果缺失 | 标记结果不明；核对产物或外部系统，不盲目重放。 |
| 审查完成，控制决定未应用 | 验证任务、schema、截止点和产物身份后才可采用；不重新运行已完成审查来改变历史。 |
| 用户已编辑，旧审查迟到 | 保存历史发现，拒绝其续行或完成权限。 |
| 快照损坏、丢失或超前 | 从有效日志重建；不依据快照单独运行。 |
| 控制器缺失或 payload 版本未知 | 兼容宿主允许只读诊断，受控执行被拒绝。 |
| 写锁冲突或持久化屏障失败 | 不授予新的动作许可；显示确切失败。 |

## 日志读取与统一视图

审查工具首先返回当前任务、最近完成轮次、未审查区间摘要和可用读取动作。分页游标绑定主 Session、逻辑格式版本、任务版本、证据截止点和读取策略版本；以事件数量和字节数双重限制响应。不得以“只返回最后一轮”替代跨轮阶段的完整覆盖。

正文按事件引用展开，保留事件类型、来源、工具结果与不明结果标记；明确说明截断、脱敏和缺失产物。会话文本和工具输出是待核对证据，不能成为更高优先级指令。工具不能让审查者任意选择 Session、修改日志、执行工作区命令，或看到读取策略排除的秘密。

“读取过”与“审查覆盖”分别记录。展示最后一页不能证明已审查前面的缺页；审查提交必须列出覆盖区间及缺口，缺证据时不推进已接受审查游标。联合时间线显示主执行、审查、决定和后续动作的因果引用，不按不同会话的时间戳强行建立全序。

compaction 产生的摘要可以帮助定位，但不替代原始证据。日志或产物被删除时，引用显示不可用并使依赖它的未决验收失效，不凭摘要补造结果。主会话删除及导出需要明确包含哪些审查日志与产物；第一版应拒绝把缺失必需引用的导出包标成可恢复。

fork 沿[任务生命周期](task-lifecycle.zh.md)生成子任务新身份和暂停状态；若裁切点截断了必要控制记录，不形成可执行恢复点。会话 clear 与 `/task clear` 分开处理：前者核对宿主实际保留的记录后创建新绑定，不能仅因会话 ID 相同就复活旧任务。跨主 Session 迁移任务不属于首版自动能力。

## 相关设计的启发

[Temporal 的事件历史](https://docs.temporal.io/workflow-execution/event)把调度与完成分别记录，用持久历史支撑恢复。这里借鉴的是动作状态与回放分离，并不引入 Temporal 服务或承诺相同执行保证。

[LangGraph checkpointer](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)保存步骤状态及待处理写入，支持中断和恢复。这里借鉴的是显式恢复点；DSH Agent 会自行选择工具，因此仍要处理执行结果不明和用户手动恢复。该比较不证明 Supervisor 比这些系统更可靠。

## 实现与验收顺序

先验证通用插件记录和缺失控制器准入；再实现确定性 reducer、快照与 inbox 恢复；之后接审查作业和最终验收。真实模型设置由[审查模型策略](review-model.zh.md)负责。宿主扩展在隔离 checkout 实验，不改日常运行实例。

必需验收包括：上述故障矩阵、重复恢复请求、同时两个进程抢写、`off` 与迟到回调竞争、fork 裁切、控制器热卸载、未知 schema、普通用户消息唤醒旧队列的反向用例，以及恢复后首次执行前的明确用户授权。注入故障测试通过后，再做真正的进程终止与重启测试；两者证据分开报告。
