# 内核能力技术试验

本文记录 [spikes/kernel](../spikes/kernel/) 中的有界试验。它使用真实 DSH Agent、循环、命令、工具、Session 与 JSONL 持久化服务，模型回复由脚本提供。这是进程内集成测试，尚未验证插件安装或 profile 启动，也不证明模型审查质量。

## 结果

试验于 2026-09-24 使用 Node 24，在 commit 为 `00102833dfaee1da9f48a3a8eae9d34005a75218`、包版本为 `0.1.7-alpha.2` 的本地 DSH checkout 上运行。十项断言通过，其中一项断言专门复现存储拒绝；该回归检查通过不意味着持久化已经可用。

| 试验 | 观察结果 | 局限 |
| --- | --- | --- |
| 独立命令与工具 | `/task` 无需模型请求即可执行；绑定 Agent 的任务工具经过真实循环调用。未挂载 Goal、Plan 或 Team 服务。 | 命令冲突、专用 preset 组合和与原生流程共存尚未验证。 |
| 挂起与审查 | 主 Agent 在第二步之前挂起；另一个 Agent 调用绑定主会话固定前缀的读取工具；释放审查后恰好进入下一次请求。 | 审查者通过 Agent 服务直接创建，输出由脚本提供。未覆盖产品子 Agent 提供方、分页或脱敏。 |
| 取消挂起步骤 | 取消使等待中的主 Agent 收敛；迟到的审查释放不会产生额外模型请求。 | 正在流式输出的审查者取消与完整 Supervisor 关闭仍待验证。 |
| 带来源记录的唤醒 | 被动注入使空闲 Agent 保持空闲；`followup` 唤醒它；两条获准输入在 `user/message` 中保留插件来源。 | 尚未实现版本预留、用户编辑优先和重复准入防护。 |
| 通过活动 Session 写入外部事件 | `Session.append()` 接受插件事件，持久化句柄也能写入；再次打开存储会话时，其未知的必需事件类型被拒绝。 | 复现了拟议活动事件写入路径的阻碍。 |
| 存储层显式事件标记 | 在事件副本上加 `ignorable: true`，再由底层持久化接口写入，可以完整重读。 | 仅用于诊断，绕过了活动 Session 的事件发布，也未证明忽略任务控制状态是安全的。 |
| 已恢复的排队工作 | Agent 重读后保持空闲，但后续用户消息会先唤醒旧督导续行，再处理用户输入。 | 仅在界面显示暂停无法阻止旧工作。 |
| 控制器存在时恢复 | `agent/created` 监听器只移除自有旧消息，等待屏障，保留待处理用户输入。 | 未覆盖控制器缺失、真实杀进程恢复或所有队列竞争。 |
| 待生效的模型选择 | 追加新的 `model/selection` 后，子级默认继承仍使用最后请求模型；显式传入路由则采用新模型。 | [审查模型策略](review-model.zh.md)需要有效选择读取入口；真实 provider 路由尚未验证。 |
| 持久化后释放续行 | 在 `runMaintenance` 中排入 followup 并等待 `flush`，独立读句柄已能看到 inbox 记录，而模型请求数仍为零；释放维护阶段后才开始请求。 | 覆盖空闲准入路径，尚未覆盖写入失败、并发编辑或真实进程崩溃。 |

## 持久化缺口

[公开 Session 追加方法](../../../deepseek-harness/packages/core/session/src/index.ts)接受事件数据和适用的模型上下文选项，但没有暴露事件信封中的 `ignorable` 标记。[已知事件列表](../../../deepseek-harness/packages/core/session/src/known-event-types.ts)由 DSH 自身源码生成，外部插件天然不在其中。[已存事件校验器](../../../deepseek-harness/packages/session/session-persistence/src/storage-contract.ts)在重新打开日志时，会拒绝没有该标记的未知事件。

测试声明 `supervisor-spike/state`，通过活动 Session 追加，经真实持久化服务写入，并断言重新打开时出现拒绝。仅做 TypeScript 声明合并不会改变运行时准入规则。测试没有通过修复或改写日志来获得通过结果。

底层正向对照证明该标记可以经过存储保留。它不是已批准的实现路径：第二个写入者会绕开活动事件流、投影和循环的持久化所有权。因此项目没有采用直接改写日志、另建权威 JSON 历史，或修改宿主生成的已知事件集合。

下一项集成决策必须同时覆盖两项义务：通过活动 Session 受支持地发布外部插件记录，以及控制器缺失或不能理解记录版本时怎样处理。仅增加事件信封元数据入口还不够。将控制记录标记为可忽略之前，必须证明受督导续行无法在缺少控制器时恢复。如果需要修改宿主，应解决通用插件持久化能力，而非依赖原生 Goal 或 Plan 服务。[督导会话设计](session-runtime.zh.md)现建议探索通用插件记录与执行准入扩展，尚未实现。

## 复现

使用已经安装开发依赖、具备现有项目引用声明产物的 DSH checkout。Node 须满足该 checkout 的 engines 要求。默认源码位置为相对本项目的同级 `../../deepseek-harness`；使用另一份 checkout 时设置 `DSH_SOURCE`。

```sh
node spikes/kernel/run.mjs --reporter=verbose
node spikes/kernel/typecheck.mjs
git diff --check
```

在本项目目录运行这些命令。测试运行器通过 checkout 的路径映射解析 DSH 源码，并使用其标准装饰器转换。严格类型检查使用 checkout 的 Host 配置与声明的项目引用，不重建依赖产物，也不宣称检查了整个 DSH 仓库。运行器和 Vite 配置是测试工具，不是应用启动器。

## 隔离与后续工作

试验不挂载应用 profile，不监听网络端口，也不调用真实模型。JSONL 存储使用新建临时目录，并在 context 释放后清理。它不使用日常 DSH home，也不重建日常 checkout。试验后观察到 3080 与 3081 日常监听实例的 PID 保持不变；不对期间无关的用户活动作断言。

仍须验证：受支持的 `dsh plugin add link:` 安装、专用 preset 组合、初始计划阶段的工具限制、持久任务投影与版本检查、进程重启后手动恢复、自有审查者取消、右侧面板，以及服务 fixture 的独立验收。下一项可执行条件是解决持久化路径，并覆盖重启与缺失控制器的反向用例；随后再运行完整隔离宿主测试。
