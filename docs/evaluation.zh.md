# 长程评测提案

**状态：研究设计。** 目前没有数据集、基准运行结果或优越性结论。本文负责评测问题与协议；[架构](architecture.zh.md)负责预期产品行为。

## 摘要

研究要回答：与 DSH 原生 Goal 或 Plan 相比，DSH 长任务督导能否在长程执行中更好地保持任务符合用户指令，并更常达到独立验收通过的结果。更快或更省成本是有用的次要证据，但不能代替任务成功。

## 对照组

| 组别 | 被测的用户工作流 |
| --- | --- |
| 原生 Goal | 固定版本 DSH 的当前 Goal 工作流。 |
| 原生 Plan | 固定版本 DSH 的当前 Plan 工作流。 |
| Task Supervisor | 拟议的统一任务工作流，包含自主续行与审查。 |

一条**产品比较**按用户平时实际使用各工作流的方式运行。另一条**机制比较**尽可能匹配模型、工具、初始上下文、执行机会和脚本化用户回复。分析时分开两条轨道：为 Plan 配备外部续行装置会改变产品工作流，但有助于区分督导的价值与续行本身的价值。

## 数据集

以固定版本的真实仓库编码任务为主。每个任务需要初始 commit、初始用户请求、明确约束、可复现环境，以及不依赖 Agent 自述的验收检查。另加受控压力案例，覆盖跑偏、重复失败方法、需求变更、过早宣称完成和高影响动作。运行任何对照组前，先冻结完整任务输入与预期评判规则。

每组使用同一任务定义和初始状态。运行期间不提供临时人工提示；必要的用户回复事先写成脚本，并对各组一致应用。跨不同随机种子或等价运行 ID 重复任务，随机化组别运行顺序，以减轻顺序与环境效应。每次运行记录模型版本、DSH commit、插件 commit、工具配置、上下文限制和宿主环境。

## 首要结果

首要指标是**遵守任务明确约束且通过独立验收的任务比例**。如果一次运行宣称完成但未通过验收、违反已记录约束，或在没有有效结果时停止，就不满足该指标。验收可结合可执行测试和针对测试无法覆盖需求的盲审。可行时，验收者不应知道产物属于哪个组别。

## 诊断指标

| 指标 | 记录内容 |
| --- | --- |
| 跑偏与恢复 | 目标或约束偏移的证据、是否得到纠正、恢复花费的轮次。 |
| 完成判断 | 缺证据的完成申请、误判通过的完成申请，以及被督导误拒的有效完成。 |
| 介入质量 | 正确发现、误报、漏报、不必要的暂停，以及要求用户作出的决策。 |
| 进展 | 有效轮次、没有新证据的重复尝试、停滞，以及到验收通过的总耗时。 |
| 资源消耗 | 模型 token、审查调用、工具调用、墙钟时间和额外资金成本。 |
| 恢复能力 | 重启后能否重建状态，以及任务是否只在预期的用户动作后恢复。 |

汇总结果之外，还要报告逐任务结果和失败案例。查看对比结果前，预先定义何为约束违反、介入真阳性、停滞和任务完成。审查判断与验收判断分开，避免由插件给自身打分。

## 结论门槛

在数据集、协议和验收标准固定且三组都运行前，不宣称督导优于 Goal 或 Plan。报告不确定性和任务类别结果，而不只报总体胜率。可信的替代方案应提升“遵守约束且验收通过”的比例，同时将误介入和用户打断控制在可接受范围；可接受的取舍需要明确写进研究设计。

## Dev Note

待定研究选项：任务数量与难度比例、确切的 DSH 基线版本、模型与随机种子可用性、时间和 token 上限、机制比较中 Plan 的续行方式、盲审规则、统计报告方法，以及可接受的介入率。正式比较前先用试运行任务验证验收规则能否复现。
