## 摘要

研究问题是：Supervisor 能否比 DSH 原生 Goal 或 Plan 更常完成符合用户指令且通过独立验收的任务，并在长程执行中保持这一能力。

先在公开测试集上建立可复现的 DSH 原生 Goal、原生 Plan 与 Task Supervisor 基线，从第一轮开始记录独立验收、完成判断、人工介入和资源指标。公开基准跑稳并形成比较报告后，再开展同一 Session 连续多个 Task／Plan／Goal 的评测。已有自建用例用于回归，不作为首批主评测；多任务会话 runner 不阻塞公开基准接入。

## 执行顺序

| 优先级 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 | 选定公开数据集版本、任务清单和外部验收器；冻结指标定义与基线交互 | 任务环境可复现，参考解与空补丁校验符合预期，三组获得相同输入与正常执行机会。 |
| P1 | 在公开数据集小样本上跑通三组端到端自动化 | 每次尝试都有日志、产物、独立评分和指标；基础设施失败与任务失败可区分。 |
| P2 | 扩大公开任务样本、重复配对运行并形成报告 | 报告完整分母、逐题结果、失败类型、任务类别分布与不确定性；保留未用于调试的样本。 |
| P3 | 同一 Session 连续多个 Task／Plan／Goal | 固定会话脚本，验证任务切换、持续约束、回归、压缩与恢复，并与每题新 Session 比较。 |

首轮建议选 6–12 个公开任务验证接入，按仓库、任务类型和难度选择，不按哪个方案更容易赢来选。这个规模用于发现接入问题；正式样本量和重复次数根据试跑方差、失败分布与可用环境确定，运行比较前冻结。公开基准的正式超时协议与放宽上限的诊断运行分开报告。

## 公开数据集选择

| 顺序 | 数据集 | 用途与接入边界 |
| --- | --- | --- |

| 连续任务候选 | [SlopCodeBench](https://github.com/SprocketLab/slop-code-bench) | 同项目需求逐步扩展；官方保留工作目录但重置 Session，同 Session 模式需单立协议。 |
| 扩展候选 | [LongCLI-Bench](https://github.com/finyorko/longcli-bench)、[LHTB](https://github.com/zli12321/LHTB)、[SWE-EVO](https://github.com/SWE-EVO/SWE-EVO) | 先核对评分、外部续行与环境门禁；不直接采用公开排行榜分数作本项目对照。 |

SWE-bench Pro V2 已开始接入。默认 QEMU 环境首题参考解校验失败，独立的 VZ/Rosetta 环境对同题取得空补丁 0、参考解 1；该校准题的 Goal、Plan、Supervisor 补丁都获得外部 reward 1.0。六题冻结样本中的 NodeBB、Navidrome 与 Open Library 已通过空补丁 0、参考解 1 的环境门禁。NodeBB 三组已封口：Goal 按时完成并获外部 reward 1.0；Plan 超时、Supervisor 因审查格式失败暂停至超时，两者截止补丁的诊断 reward 都为 1.0，但主指标失败。Navidrome 三组均按时完成且外部通过。首轮初始三组批次的 Open Library 尚未投递模型，后续 P2 另见阶段报告。校准题不计入冻结样本；两道冻结题仍不能支持总体比较。固定数据集 commit／版本、样本 ID、容器 digest、验收器版本及初始仓库提交；运行前检查许可证与环境要求。SWE-bench Pro V2 官方镜像标注为 linux/amd64，需逐题验证参考解与空补丁。不要将不同版本分数合并，或将修改了任务、交互、联网规则或时间上限的结果称为官方成绩。

公开编码任务通常按单题组织。同一任务内部可以包含多次模型交互与续行，但这不等于同一 Session 连续多个用户任务。后者在 P3 单独定义；不用强行把不同仓库和基础提交的题目拼到一个工作区。

### 2026-09-28 长程基准调研

下述来源是别人已发布的运行证据与本项目的接入建议。本项目尚未运行这些新候选；旧 P2 不因本次调研换题、换版本或追加救场。增强独立检查的 SWE-bench Pro 预检发现：NodeBB 快照超过条目上限、Navidrome 的相对悬空链接导致捕获失败、容器内宿主没有 Docker 检查入口。这些属于快照和检查部署问题，不能推断数据集无法由 DSH 执行；换成另一容器基准仍须解决检查入口。

| 候选 | 别人实际跑过的证据 | 对本项目的价值与限制 |
| --- | --- | --- |
| Terminal-Bench 2.1 | [Maka 九 harness 报告](https://github.com/apache/maka/blob/main/docs/eval/terminal-bench-2.1-deepseek-v4-flash-nine-arm.md)公布 89 题逐题 CSV，DSH 在 DeepSeek V4 Flash 下为 65/89；DSH 后跑且部分基础设施修复后重跑，属于描述性结果。 | 最直接的 DSH 接入参照。其 [adapter](https://github.com/apache/maka/blob/main/packages/eval/README.md)使用 JSON-RPC minimal composition；不能视为已验证本插件或 Goal／Plan。复用官方验收并验证后台服务存活、命令超时和依赖安装。 |
| DeepSWE v1.1 | [官方题库](https://github.com/datacurve-ai/deep-swe)含 113 道原创工程任务；[DeepSeek 官方复现说明](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/evaluation/README.md)提供固定 Pier／题库版本和 SDK `dsh-minimal` adapter；[FrontierHarness](https://github.com/frontier-harness-eval/eval/blob/main/benchmark.json)亦在 9 道 DeepSWE 与 21 道 Terminal-Bench 上发布 DSH 多 profile 结果。 | 推荐的工程主线：提交补丁后在干净的独立容器评分。SDK minimal 不是本插件 preset；公开样本和网络环境变更也不构成等价对照。按任务要求配置资源，不能沿用旧 P2 的 1 CPU／4 GiB 并称官方复现。 |

| LongCLI-Bench | [论文](https://arxiv.org/html/2602.14337v2)报告 Codex、Claude Code、OpenHands 在 20 题上的三次重复；[runner](https://github.com/finyorko/longcli-bench)提供需求、回归与步骤评分。 | 可测计划失效、早期停滞与回归；已有人报告并关闭的[环境／评分缺陷](https://github.com/finyorko/longcli-bench/issues/4)要求逐题确认修复版本。QEMU、并发测试及隐藏评分反馈须先校准；未找到 DSH 完整公开复现。 |
| LHTB | [论文](https://arxiv.org/abs/2607.08964)发布 46 道长终端任务和密集奖励；[仓库](https://github.com/zli12321/LHTB)公布 Terminus-2 等运行，常规预算为 90 分钟。 | 可做更长的单任务压力测试。30/46 题启用隐藏验收失败后的外部自动续行，这会影响本项目的续行／完成判断比较；官方轨道与不反馈的产品轨道分开。历史结果早于验收器隔离与二值反馈改动，不与新批次混合；未找到 DSH 完整公开复现。 |

建议接入顺序是 Terminal-Bench 控制题 → DeepSWE 工程小样本 → SlopCodeBench 连续任务；LongCLI 与 LHTB 在各自协议校准后扩展。先做无模型的参考解、无修改产物与检查运行器门禁；再冻结未用于调试的题单、四组（Goal／Plan／仅日志审查／独立检查审查）、重复数与资源。小样本用于接入和失败分类，正式替代结论仍遵循[结论门槛](#结论门槛)。选题按固定元数据规则，不按哪组能赢来筛。

保留严格通过、部分需求完成、旧功能回归、错误完成、合法等待、内部故障、基础设施失败及全部 Session 用量。评估长程性还要记录活动时长、轮次、压缩和进展轨迹；长超时配置不等于实际持续长程执行。产品审查只能使用公开需求、产物与自己的检查，不能获得外部隐藏评分反馈；纠偏与误暂停未经盲审标注仍为缺失。

## 首轮比较协议

首轮比较原生 Goal、原生 Plan、Task Supervisor。主 Agent 使用相同的模型路由、推理设置、工具权限和上下文限制；记录实际解析出的模型。Supervisor 审查默认沿用主模型；审查和子 Agent 的消耗全部计入。任务在各组独立环境中从同一快照启动，随机化运行顺序，并按任务配对重复。

产品轨道给各组正常的原生交互与预先规定的批准机会。运行前定义 Plan 的批准、开始执行、空闲、等待用户和结束条件；不能把合法等待直接记成失败，也不能临时补发救场提示。额外续跑由评测器提供的实验标为机制轨道，与原生产品成绩分开。协议未冻结的题只作为开发试跑。

正式优越性结论仍需下述 Lead–Worker Team 对照，以及保留状态与续行但关闭语义审查的诊断组。首轮三组结果只支持这三种工作流在选定任务上的比较；不能据此宣称审查机制本身胜出或优于 Team。

外部验收器与产品审查独立。隐藏测试、参考解和评分材料置于被测 Agent 无法访问的位置；在独立副本中验收，保留原始产物。隐藏失败不反馈给 Agent 反复修到通过。允许 Agent 使用题目公开测试。先验证参考解通过、空补丁按题目预期失败，避免评分器本身产生虚假成功。

## 对照与证据规则

Team 组使用根 Lead 加一个 Worker，Lead 组合原生规划和 Goal 续行，并明确负责验证与纠错。先验证组合 preset 和真实任务控制权限；提供等价的任务要求、产物与执行证据访问。若审查者使用更强模型，为 Team 匹配资源或单列模型分配实验；差异不能归因为督导机制。Team 配置与产品职责区别见[首个原型](prototype.zh.md)。

关闭语义审查的消融组保留相同的任务状态、规划、续行和模型配置，由同一外部验收器评分。可选比较仅阶段审查与阶段审查加兜底观察，联合报告暂停与成功，避免过度打断被误记为有效监督。

各组自主规划，用共同的外部结果里程碑比较进展；不向某组提供隐藏参考计划，不以各组自行拆分的阶段数量计分。阶段应关联产物、检查和需求变更后的重开条件。给所有组同一预设计划属于单独诊断。运行前冻结公开任务、约束、允许改动、验收规则、事件脚本和初始环境。

保护外部验收材料；题目允许时可修改项目测试，不能把所有测试改动自动判失败。记录已跟踪与未跟踪产物。测试无法覆盖的需求使用预先制定的盲审规则，可行时隐藏组别；明确不可检查要求与证据缺口，不把它们算成已满足。

## 评测层次与开发回归

下面是证据类型，不是执行先后。公开基准按[执行顺序](#执行顺序)推进；回放和生命周期回归用于维护已修复行为、分析失败。

| 层次 | 能说明什么 | 约束 |
| --- | --- | --- |
| 历史轨迹回放 | 审查发现问题、引用证据和选择介入的能力。 | 只给当时可见的证据前缀；包含正常推进和合理重复尝试，避免总挑错也得高分；不能证明介入改善结果。 |
| 确定性宿主回归 | 状态转换、取消、持久恢复和过期决策拒绝。 | 覆盖编辑时审查在途、clear 时续行排队、关闭时超时待触发、重启后手动恢复；容量和 fork 按对应能力实现进度验证。 |
| 端到端比较 | 从相同输入到独立验收的任务结果。 | 采用冻结任务与规定对照，产品审查属于被测系统，评分由外部负责。 |

开发用例覆盖短修复、多阶段功能、需求变更、反复无效尝试、缺证据的完成和未汇报里程碑的长阶段。短任务观察不必要开销，长阶段观察跑偏漏检；这些用例不取代公开主评测或未用于调试的保留集。

## 必须采集的指标

指标从首轮接入就采集，不能在跑完后只挑有利的数字。功能通过、约束遵守和完成声明分别保存，再计算汇总。

| 指标 | 定义与口径 |
| --- | --- |
| 独立验收通过率 | 通过外部验收的任务运行数／具有有效评分的任务运行数；同时报告计划运行数、总尝试数与无法评分数。 |
| 约束合规成功率（首要指标） | 外部验收通过且所有可检查的明确约束满足的运行数／具有有效评分的运行数；未完成和达到执行上限均计失败。 |
| 错误完成率 | 已宣称最终完成但外部验收或约束检查失败的运行数／已宣称最终完成且可评分的运行数；同时给出原始计数。 |
| 停滞与结束原因 | 区分完成、合法等待、无进展停止、资源上限、模型或工具错误、基础设施失败；每次运行记录最后状态。 |
| 人工介入 | 分别计预设批准与额外救场次数；主比较不允许临时救场，救场后的结果属于诊断。 |
| 审查有效性 | 对有独立标注的审查点报告真实发现、误报、漏报和无必要暂停；没有标注时仅报告原始审查与暂停次数。 |
| 进展与资源 | 总耗时、活动与等待耗时、主 Agent／审查／其他子 Agent 的轮次和 Token、工具调用与审查次数；可获得时记录费用。 |
| 跑偏与纠偏 | 有独立标注时记录首次可观察偏离、发现位置、恢复轮次与持续时间、缺证据的完成申请和误拒的有效完成；无标注则保留轨迹供分析。 |
| 重复运行可靠性 | 按题记录多次运行通过情况与配对差异；统计不确定性以题目为单位，不能把重复运行当作新题。 |

分母为零时报告“不适用”，缺失日志或用量报告为“缺失”，不填零。无法评分的基础设施失败必须进入尝试清单；事先规定有限重试策略，保留全部失败和重试记录，报告失败数量及其对覆盖率的影响。费用和速度是次要指标，不用加权总分覆盖成功率与错误完成率。

P3 额外报告整段 Session 全通过率、按任务位置的通过率、旧功能回归率、任务边界错误率和恢复成功率。届时以 Session 为主要统计单位；同一条链里的多个任务存在依赖，不能当作独立样本。

## 自动化与结果产物

运行器通过 DSH 原生接口或无头 profile 驱动任务，浏览器用于另行验证 UI。接入可复用公开基准的环境与验收流程，不先重建整套评分系统。隔离环境按现有 Skill 与注册表管理；每个正式任务从固定快照开始，不继承手工测试的文件残留。

每次运行至少保存以下信息；具体文件格式在 runner 接入时确定：

- 运行清单：数据集版本、任务 ID、对照组、重复运行 ID、DSH／插件版本、模型设置、工具与上下文配置、批准策略和执行上限。
- 原始证据：主 Session 与审查／子 Agent 日志、状态事件、开始结束时间、补丁及必要的未跟踪产物。
- 外部评分：验收器版本、检查结果、约束检查、完成声明、结束原因、错误和重试关联。
- 指标明细：逐次运行数据、逐题汇总、各组配对比较、任务类别结果和失败案例。

调节审查策略前按仓库或任务类别划分开发集与保留集。预先定义约束违反、介入真阳性、停滞和最终完成；如模型支持随机种子，记录种子，否则用可追溯重复运行 ID。

报告同时展示每个数据集的原始验收结果与我们的合规／完成判断指标。不同数据集各自报告；如需汇总，先固定权重与聚合方式。开发样本与冻结保留集分开，不用反复调过的样本得出泛化结论。

## 后续多任务 Session

公开基准基线稳定后，增加固定会话脚本：同一 Session 中依次创建 Task 1…N、Goal 1…N 或 Plan 1…N，每个位置对应同一用户任务；组内保留自己的历史和真实工作成果。另设每题新 Session 的对照，区分题目难度和上下文累积影响。

样本覆盖独立任务切换、同项目持续演进、需求修改与压缩／暂停／重启恢复。明确 Session 全程约束和任务局部约束；后续任务不能偷偷替换为参考成果。依赖链失败后的诊断若使用标准前置快照，必须另行标记。首版可用账单工具持续演进等可执行案例，之后再扩展真实项目。

下一任务按预先规定的任务结束或上限条件投递，不能等待隐藏评分通过才投递。中途变更按各组共同可观察的事件触发，记录交付与生效位置；不再用 Supervisor 阶段审查与原生组首次写文件作为不同触发条件。可参考 [χ-Bench-Marathon 的同 Session 多任务协议](https://arxiv.org/html/2605.16679v1)，其业务领域与评分结果不直接迁移到 DSH。

## 结论门槛

三组试跑仅报告选定任务上的观察。正式替代结论需要冻结数据集、协议和验收标准，完成原生 Goal、Plan、Supervisor 与 Team 对照；审查机制的归因还需消融证据。报告不确定性、任务类别与失败案例，并提前规定可接受的误介入和用户打断程度。如果 Team 用更简单配置达到同样效果，应收窄结论或复用该机制。

## 复用来源

本地 [forever-subagents 评测设计](../../../forever-subagents/docs/eval-design.md)提供 fixture、任务、写入范围、检查、转录和运行结果的概念。[DSH harness 设计](../../../forever-fish/docs/harness-eval-design.md)提供回溯分析、机制检查和端到端比较的分层方式。[WorkDAG 设计](../../../forever-fish/docs/workdag-eval-design.md)提供证据完整性检查和受控恢复故障。这些是来源提案，不证明其中规划的 runner 或数据集已经可用。已有[轨迹分析脚本](../../../forever-fish/eval/analyze_dsh.py)是候选代码，复用前须对照固定版本的 DSH 事件格式验证解析器。

复用任务输入、写入范围、验收、转录和结果概念，补充版本化约束、脚本化事件与外部评分；资源指标独立报告。DAG 指标观察真实依赖、阶段进展、恢复与正确停止，不以并行数量代替成功。旧 Jev 的结构化审查、终态与递归防护经验需重新验证；旧网站演示不进入主评测。轨迹导出是可选适配，本地产物应足以复现，不依赖看板。

来源文档中的基准数量、模型分数、SDK 命令和基础设施估算不作为当前事实；接入时核对一手资料与实际环境。
