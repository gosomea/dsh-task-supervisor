# 长程评测提案

**状态：研究设计＋开发试跑。** [Goal/Plan/Supervisor 两题产品试跑](../eval/pilot-v1/results-20260926.zh.md)、[分轮时序回归](../eval/reliability-v1/results-20260927.zh.md)和[多阶段需求变更开发题及结果](../eval/long-horizon-dev-v1/results-20260927.zh.md)提供不同层次的证据；尚无冻结的长程留出集或优越性结论。本文负责评测问题与协议；[架构](architecture.zh.md)负责预期产品行为。

当前执行顺序见 [Eval Notes](notes-eval.zh.md)：先跑公开测试集及必需指标，再开展同一 Session 多任务比较。

## 摘要

研究要回答：与 DSH 原生 Goal 或 Plan 相比，DSH 长任务督导能否在长程执行中更好地保持任务符合用户指令，并更常达到独立验收通过的结果。更快或更省成本是有用的次要证据，但不能代替任务成功。

## 对照组

| 组别 | 被测的用户工作流 |
| --- | --- |
| 原生 Goal | 固定版本 DSH 的当前 Goal 工作流。 |
| 原生 Plan | 固定版本 DSH 的当前 Plan 工作流。 |
| Task Supervisor | 通过独立 Supervisor 命令（暂定 `/task`）进入的拟议统一任务工作流，包含自主续行与审查。 |
| Lead–Worker Team | 根 Lead 使用原生规划和 Goal 续行，委派给一个 Worker 并明确验证其工作；先验证组合 preset。 |

一条**产品比较**按用户平时实际使用各工作流的方式运行。另一条**机制比较**尽可能匹配模型、工具、初始上下文、执行机会和脚本化用户回复。分析时分开两条轨道：为 Plan 配备外部续行装置会改变产品工作流，但有助于区分督导的价值与续行本身的价值。

[Team 对照](prototype.zh.md)用于检验 Supervisor 是否比有能力的 Lead 协调 Worker 提供额外价值，是必要对照。尽可能匹配证据访问与模型分配；存在差异时单独报告，不能直接归因为督导机制。

## 数据集

以固定版本的真实仓库编码任务为主。每个任务需要初始 commit、初始用户请求、明确约束、可复现环境，以及不依赖 Agent 自述的验收检查。另加受控压力案例，覆盖跑偏、重复失败方法、需求变更、过早宣称完成和违反明确任务约束。运行任何对照组前，先冻结完整任务输入与预期评判规则。

每组使用同一任务定义和初始状态。运行期间不提供临时人工提示；必要的用户回复事先写成脚本，并对各组一致应用。跨不同随机种子或等价运行 ID 重复任务，随机化组别运行顺序，以减轻顺序与环境效应。每次运行记录模型版本、DSH commit、插件 commit、工具配置、上下文限制和宿主环境。

## 三层评测

第一层，将历史失败整理为开发案例，标注相关目标、约束、证据和首次可观察偏离。固定检查点时，只向审查者展示当时可见的证据前缀。加入正常推进和合理重复尝试作为负例，否则总是挑错的审查者也能得高分。报告漏报、误报、证据质量和介入选择。离线回放衡量判断质量，不能证明建议能改善执行结果。

第二层，在隔离宿主运行确定性的生命周期与故障注入场景，由明确断言检查状态转换、取消、持久恢复和过期决策拒绝。通过这一层证明控制可靠性，不能证明模型完成能力。

第三层，将相同的留出任务 fixture 交给原生 Goal、原生 Plan、Supervisor、Lead–Worker Team 对照和保留续行但关闭审查的诊断组。主 Agent 与审查者不能访问外部评测器的私有测试材料或标注。产品中的最终验收器属于被测系统；基准评分由另外的评测过程依据自己的证据和检查完成。

## 任务记录与阶段证据

| 记录部分 | 内容及可见范围 |
| --- | --- |
| 公开任务 | 初始请求、约束、可观察验收标准、允许的改动和必要环境说明；各组一致。 |
| 可复现 fixture | 固定仓库与初始快照、依赖环境、重置方式和来源。 |
| 评测包 | 外部检查、参考结果和证据标注；保护其不被修改，会暴露答案的部分不提供给被测系统。 |
| 脚本化事件 | 需求更新或故障注入，预先指定触发条件，各组使用相同载荷，并记录是否到达触发条件。 |
| 运行清单 | 工作流、模型与推理设置、版本、执行上限、重复运行 ID、转录、产物和外部评分。 |

正式端到端比较已确定的默认规则是：各组自主规划，使用同一套外部验收标准和评测程序。每组获得相同的目标、约束和公开验收要求。数据集里程碑描述可独立观察的结果，不提供仅 Supervisor 可见的隐藏参考计划。阶段定义应连接目标与产物或检查，并说明相关要求变化后何时重开。用共同的外部证据里程碑衡量进展，不比较各组自称完成了多少阶段。给所有组同一份预设计划属于独立诊断实验，结果与主比较分开报告。

保护外部验收检查；任务允许时可以修改项目测试。除测试完整性证据外，还要捕获已跟踪和未跟踪产物的变化。不能把所有项目测试修改都自动判失败，也不能只依赖已跟踪文件的 Git diff。脚本化变更在预先指定的可观察事件或工作量检查点触发，不在看到某组行为后临时挑选时间。

历史失败和普通成功工作整理为开发回归；首批主评测使用公开数据集，选题与执行顺序由 [Eval Notes](notes-eval.zh.md)维护。调节审查策略前，按仓库或任务类别冻结独立留出集。重复配对实验，按任务维度报告不确定性；同一题反复运行不等于增加独立题目。预先规定基础设施错误、中断和资源上限停止的处理方式，保留每次尝试，并报告完整结果分母，防止重试悄悄抬高分数。

## 首批实验

先在隔离 DSH 场景验证生命周期行为：容量溢出、审查进行中编辑、续行排队时 clear、超时待触发时关闭、执行中断后重启，以及 fork 不继承执行权限。这些检查证明控制正确性，不能证明任务完成效果更好。

开发回归覆盖六类任务：短修复、多阶段功能、执行中需求变更、反复无效尝试、缺证据的完成声明，以及始终不汇报里程碑的长阶段。短修复检查督导是否增加不必要工作；长阶段检查仅靠里程碑审查是否漏掉跑偏。试跑任务属于开发数据；比较结论使用另行保留的任务。

增加一个诊断消融组，保持同样的任务状态、规划、续行和模型配置，关闭语义审查，再由同一个独立评测器评分。如果提升只出现在对比续行机会更少的基线时，仍不能证明审查防止了跑偏。可选的频率比较可测试仅阶段审查与阶段审查加兜底的差异。共同报告打断次数和验收通过率，防止把过度暂停误报成成功。

## 首要结果

首要指标是**遵守任务明确约束且通过独立验收的任务比例**。如果一次运行宣称完成但未通过验收、违反已记录约束，或在没有有效结果时停止，就不满足该指标。验收可结合可执行测试和针对测试无法覆盖需求的盲审。可行时，验收者不应知道产物属于哪个组别。

## 诊断指标

| 指标 | 记录内容 |
| --- | --- |
| 跑偏与恢复 | 目标或约束偏移的证据、是否得到纠正、恢复花费的轮次。 |
| 完成判断 | 缺证据的完成申请、误判通过的完成申请，以及被督导误拒的有效完成。 |
| 介入质量 | 正确发现、误报、漏报、不必要的暂停，以及要求用户作出的决策。 |
| 进展 | 有效轮次、没有新证据的重复尝试、停滞，以及到验收通过的总耗时。 |
| 资源消耗 | 模型 token、审查调用、工具调用、墙钟时间和额外资金成本。 |
| 恢复能力 | 重启后能否重建状态，以及任务是否只在预期的用户动作后恢复。 |

汇总结果之外，还要报告逐任务结果和失败案例。查看对比结果前，预先定义何为约束违反、介入真阳性、停滞和任务完成。审查判断与验收判断分开，避免由插件给自身打分。

## 结论门槛

在数据集、协议和验收标准固定且全部产品组都运行前，不宣称督导优于 Goal 或 Plan。报告不确定性和任务类别结果，而不只报总体胜率。可信的替代方案应提升“遵守约束且验收通过”的比例，同时将误介入和用户打断控制在可接受范围；可接受的取舍需要明确写进研究设计。
