# 督导对话与审查恢复方案

**状态：设计提案，尚未实现。更新：2026-09-28。** 本文规划草案对话、审查故障恢复和审查频率实验。现有功能以[实现状态](../../implementation.zh.md)为准；本轮不改变运行代码、部署或冻结评测结果。

## 摘要

建议把新建任务融入贯穿主 Session 的督导对话。用户可以先讨论想法、整理需求，也可以直接创建明确的任务。创建只把已确认的要求交给主 Agent 规划；首次自主执行仍等待初始计划批准。审查协议故障先尝试一次有限补交，耗尽后展示故障与恢复入口；真正的用户决策单独处理。

## 现状与依据

当前历史任务页面有独立的新建表单；`consultation.open` 必须有当前任务，督导对话绑定单个任务，换任务后旧对话不能控制新任务。因此“先聊清楚再建任务”目前没有完整入口。对话已有原生 Session、只读证据工具和用户指令收据，可以扩展这些机制，复用原生输入框和压缩能力。实现位置是 `src/consultation.ts`、`src/panel-api.ts` 和 `src/client/index.tsx`。

[NodeBB 冻结评测](../../../eval/swebench-pro-v2/frozen-nodebb-20260928.zh.md)中，审查者用文字给出结论，却没有成功记录 `task_review_decision`，约在 1,761 秒暂停。暂停补丁通过外部测试，但到 3,000 秒未完成，主指标仍为失败。这直接支持协议恢复与故障分类修复；不能把文字结论或外部补丁得分补算为任务完成。

[Navidrome 冻结评测](../../../eval/swebench-pro-v2/frozen-navidrome-20260928.zh.md)按时完成，发生七次审查，包括两次进展观察。它显示了审查开销，尚不能证明这两次观察无用。当前代码默认在安全步骤边界按 24 条工具结果、300,000 毫秒或连续三次工具错误触发进展观察；没有新工具结果时不单凭时间触发。审查策略文档中的“三轮或二十条结果”是早期提案，本轮记录实际代码作为实验基线，不把它认定为最佳频率。

## 从对话形成任务

### 入口与选择

保留“任务详情”和“督导对话”两个 Tab。无任务时默认进入督导对话；历史列表中的“讨论新任务”也打开同一入口，移除独立的大文本框。对话底部保持原生输入框，顶部展示当前讨论对象；历史列表继续提供只读详情。

| 用户意图 | 建议交互 | 对主任务的影响 |
| --- | --- | --- |
| 先讨论 | 输入宽泛想法，督导询问最影响范围的一两个问题，给出建议起点 | 保存讨论；不创建任务、不启动主 Agent。 |
| 整理需求 | 明确请求“整理成任务要求”或“润色 prompt”，得到可编辑的草案 | 保存草案版本；没有执行授权。 |
| 创建草案任务 | 草案旁点击“创建任务”，或明确输入“按这份草案创建任务” | 将确认版本的完整要求写入主 Session，由主 Agent 提交计划。 |
| 直接创建 | 选择“直接建任务”模式发送，或输入 `/task new <完整目标>` | 沿用同一控制器；明确请求可直接进入规划。 |
| 普通进度问询 | 对当前任务提问，读取最新状态与证据 | 不打断执行或审查。 |

默认发送方式是讨论，当前模式始终可见。督导可以建议创建，但不能凭模型对用户语气的猜测调用创建工具。“可以”“继续”等短回复只关联眼前明确的提议；存在多个候选时先明确目标。按钮和文字操作都绑定同一草案版本与操作收据，不增加两套控制路径。

没有任务时，草案和督导的可见回答也跟随用户语言，中文作为配置的回退语言；创建后将该偏好传入任务。语言和讨论对象都不能充当操作授权，使用中文回答并不代表可以替用户执行操作。

例如“我要开发一个我的世界”：先建议一个可玩的体素原型，并明确运行平台、首批玩法和验收方式；用户可以继续细化，也可以接受这个起点。整理后的草案展示目标、范围、约束、验收方式及尚未确认的假设。简单需求不必填写固定问卷；涉及关键选择时询问，普通默认值写进草案供用户修改。展示草案版本后，用户创建任务；主 Agent 随后生成执行计划，用户批准该计划后才自主执行。

### 会话与草案归属

建议每个主 Session 有一个持久督导对话，讨论上下文显式标为“新任务草案”“当前任务”或“历史任务”。每次模型请求注入当前上下文身份和有界状态，旧任务的命令不能随界面选择变化转移到新任务。独立审查仍使用独立 Session，咨询对话不能代替审查者裁决，也不能执行工作区工具。

草案是对话中的版本化提案，不占已创建任务的执行名额。首版每个主 Session 只保留一份待创建草案，旧版本留在原生日志，避免无上限的隐形队列。草案最少记录 `draftId`、版本、完整要求、未决问题、来源用户消息及创建结果引用；另行维护可重建的当前草案投影。讨论历史属于督导 Session；创建时将确认文本、来源与收据持久写入主 Session，之后正式任务要求以主 Session 为准。

当前任务执行期间可以讨论下一项，但首版仍不自动创建或排队执行另一任务。界面提示“草案已保存，当前任务结束后可创建”，禁止悄悄修改当前目标。当前任务完成不关闭对话，也不自动晋升草案；历史任务选择仅改变只读详情。需要修改当前任务时使用明确的编辑请求，使旧审查和续行失效。

### 创建、恢复与迁移

创建请求绑定主 Session、草案身份与版本、当前任务身份与修订号、授权来源和幂等键。控制器核对草案仍有效、创建名额可用、最新用户要求和持久化屏障，然后记录正式任务；任务记录包含该请求身份。超时重试先查既有任务和收据，不能重复创建。跨两个 Session 的记录不假装是原子事务；主 Session 的创建提交为生效点，督导侧通过该提交恢复显示结果。

用户确认创建的是要求草案，首次计划批准仍是已有执行门禁。对同一份草案不额外弹出重复确认。创建可以启动只读规划，不能越过计划批准。用户直接 `/task new` 的流程继续可用。

| 情况 | 拟议处理 |
| --- | --- |
| 压缩 | 保留主 Session 绑定、讨论对象、草案版本及来源引用；不能从模型摘要重建授权。 |
| 重启或重新打开 | 恢复对话、草案和任务状态；不自动创建、不自动续行，未完成任务等手动恢复。 |
| 清除任务 | 正式任务进入历史；已有草案可保留，旧任务的审批和命令失效。 |
| 原生会话清空上下文 | 创建新的讨论上下文边界；旧草案需明确重新选择，旧短回复授权不能沿用。宿主具体事件在实现前验证。 |
| fork | 新的主 Session 使用自己的督导绑定；旧草案可明确复制为新草案，不能控制父会话或继承未完成的创建授权。 |
| 旧版任务对话 | 保留原日志与只读访问，不改写旧事件；新入口引用旧对话，不自动合并历史为新的控制指令。 |

## 四项审查修复

### 1. 协议缺失后的有限补交

建立持久审查作业身份，固定任务修订、计划版本、节点与尝试、审查类型、证据截止点、已解析模型配置及 reviewer Session。若正常结束但没有成功记录决策，默认允许一次补交轮次；配置须有有限上限，整个作业受总时限约束，补交不重置总时限。具体时限根据已有运行分布确定，实施前固定默认值。

补交继续同一 reviewer Session，保留已读证据及工具约束。提示明确说明“上一轮没有有效决策记录”，列出可用工具、有效字段和前次验证错误，要求基于原截止点提交。它不重做主任务，不新建审查 Session，也不从“Decision: pass”之类文字推断通过。工具调用 schema 或证据引用无效可纳入同一补交额度；语义上的证据不足应正常提交 `revise` 或 `needs-user`，不能靠格式重试强行得到通过。

补交仅用于可以确认没有有效提交的协议问题。模型服务故障、读取故障、超时和取消分别分类；未知结果先核对持久记录，不盲目重试整个作业。如果决策已成功持久提交，随后的结束错误不能覆盖它；应用决策仍检查作业身份、任务版本和有效状态，只能应用一次。

编辑、暂停、关闭督导、clear、新用户要求和运行上下文失效都可撤销旧作业。迟到结果留作历史但不应用。重启不自动补交；用户请求恢复时先核对作业与状态。原截止点仍有效且 reviewer Session 可恢复时可继续该作业，否则记录旧作业失效并创建有明确来源的新审查作业，不能伪称同一次重试。

### 2. 内部故障与用户决策分开

| 结果 | 状态和显示 | 用户动作 |
| --- | --- | --- |
| 有效 `pass` / `revise` | 应用正式审查决定，展示结论和证据 | 正常继续或补做。 |
| 有效 `needs-user` | 等待具体用户选择，说明矛盾、缺少的信息或授权 | 回答该问题或调整任务。 |
| 正在补交协议决定 | 保持审查门禁，显示“正在恢复审查结果 · 1/1” | 可暂停或关闭督导。 |
| 补交耗尽或内部故障 | 暂停，显示“审查故障”，保留错误类别与恢复入口 | 重试审查、查看原始审查对话、暂停或关闭。 |
| 用户暂停或关闭 | 保留用户操作原因 | 只有明确手动恢复才重新准入。 |

首版可沿用 `paused` 阶段并增加类型化暂停原因，避免为每种故障扩展整个任务状态机。决策和故障应为不同记录类型；内部错误不能生成假的 `needs-user` 结论。界面隐藏无意义的“批准”动作，提供确切的“重试审查”按钮与等价控制入口。用户重试授予审查恢复许可；是否可以续行仍由原计划批准、手动暂停、重启和最新指令共同决定，按钮不能旁路执行门禁。

### 3. 保留失败身份与证据

在模型运行前持久记录作业，之后分别记录每次尝试、补交开始、失败、有效决定、应用或过期结果。所有路径覆盖计划、进展、节点及完成审查，不能只修复一次阶段汇报的 catch。UI 与评测从同一记录投影读取，内部字段在“诊断详情”展开，默认用用户语言解释影响。

| 字段组 | 最少内容 |
| --- | --- |
| 作业身份 | `reviewJobId`、任务 ID/修订、计划版本、检查点、节点尝试、证据截止点、运行上下文身份。 |
| 模型与 Session | reviewer Session ID、解析模型身份；创建前失败则 Session ID 可空并说明失败位置。 |
| 尝试 | 尝试序号、补交次数/上限、开始与结束时间、触发原因。 |
| 失败 | 错误类别、可阅读摘要、原始事件引用、是否可重试、结果是否已知。 |
| 成功 | 决策工具成功事件引用、支持证据、应用结果或过期原因。 |

错误类别至少区分协议缺失、决策验证失败、模型服务故障、证据读取失败、超时、用户取消和作业过期；稳定错误码供程序统计。恢复收据与生效点必须可重放、去重。旧 schema 继续可读；无法判断旧 `needs-user` 来源时显示“旧记录，原因未分类”，不能靠文本猜测迁移成内部故障或改写历史。

### 4. 进展审查频率实验

保留计划就绪、阶段完成、实质修订和最终完成等必要审查。进展观察负责主 Agent 长期不报告时发现偏离，应根据新证据和任务进展决定价值。先记录每次触发的原因、时间/工具增量、已覆盖窗口、审查耗时、决定、是否交付纠偏、之后是否改变行为及最终外部验收。

对同任务版本、检查点与证据截止点去重；多个进展触发合并。正式节点审查已覆盖的证据不能再次单独触发相同进展审查，但进展通过不能代替节点或最终验收。连续工具失败只是观察信号，正常探索或长工具运行不等于停滞；单纯超过阈值不直接暂停。

| 实验组 | 用途 |
| --- | --- |
| 当前代码策略 | 24 条结果 / 300,000 毫秒 / 连续三次错误，作为可复现基线。 |
| 必要检查点 + 校准后的进展兜底 | 根据试跑确定阈值、合并规则及冷却条件，再冻结配置。 |
| 仅必要检查点 | 诊断进展观察的增量收益；不预设为默认产品策略。 |

所有组使用相同协议恢复机制和模型，避免把协议修复收益误算成审查频率收益。用标注的实际偏离与合法探索判断误暂停和漏检；没有纠偏的通过审查不自动等于无用。联合报告按时外部验收成功、纠偏有效率、误暂停、未发现偏离、审查等待和全部 Session Token。开发中先采集数据，完成受控比较后才更改默认策略。

## 开发顺序与验收

每步完成相关验证、更新实现状态和证据，再独立 commit、push。下表是未来执行门禁，本轮没有执行这些开发测试。

| 步骤 | 为什么与主要范围 | 验收门禁 |
| --- | --- | --- |
| A：审查记录与故障分类 | 先修可追踪性；`state-schema.ts`、`state.ts`、`reviewer.ts`、`index.ts` 全部审查入口 | 四类检查点失败均保留作业/Session/原截止点；故障不生成决策；旧日志可重放，错误引用可打开。 |
| B：有限补交与恢复控制 | 依赖 A；同 reviewer Session 的补交、总时限、取消及恢复动作 | 零提交→一次补交成功；重复无提交→故障暂停；已提交后结束报错、重复回调、编辑/off/重启/迟到结果均不重复应用或意外续行。 |
| C：主 Session 督导对话与草案 | 扩展 `consultation.ts`、持久投影、控制收据和 `panel-api.ts` | 无任务可讨论；润色不创建；指定草案版本只创建一次；并发点击/文字、陈旧版本、当前任务忙、压缩/重启/fork 不串任务或继承授权。 |
| D：统一入口与故障 UI | 依赖 A、B、C；`client/index.tsx`、`consultation.tsx`、`task-store.ts`、原生组件/样式 | 无任务/进行中/完成/历史都有明确对象；原生输入框与两个 Tab 正常；主 Session 保留小 DAG 与执行者进度；故障和用户问题的按钮正确，主 Agent 输出保持原样。 |
| E：进展观察记录与实验开关 | 依赖 A、B；`observation.ts`、配置和 eval runner | 触发与去重可复现；三策略只改变进展观察；正式完成门禁不变，runner 统计故障/误暂停/资源。 |
| F：联合隔离验收与新评测 | 依赖前五步；固定发布候选版本 | 真实模型任务和恢复测试通过；冻结新比较协议，给出独立外部评分与完整分母，报告残余问题。 |

建议先执行 A、B，消除已确认的续行故障，再执行 C、D 完成用户入口。E、F 根据记录决定审查频率，不提前承诺减少几次审查。允许在 A 的记录结构确定后设计 C，但首版不引入并行任务队列或新的通用 Agent Team 调度。

## 评测与上线条件

隔离验证沿用 `dsh-plugin-isolated-test` 的登记与复用流程：先查本插件已有隔离环境，复用其部署/profile；功能工作区从 TMP 新建独立样本，不靠网页让用户选择目录，不改日常环境。真实模型沿用日常 DSH profile 的模型选择，记录解析身份。重启、协议错误和旧格式使用确定性故障样本补充真实模型测试。

草案交互至少验证宽泛游戏想法、清晰只读任务、当前任务中筹备下一项、完成后连续第二项，以及压缩/重启后继续讨论。执行层至少跑通计划→批准→节点→完成，协议补交后完成，补交耗尽后明确手动恢复，以及只有用户才能解决的问题。故障样本不能用普通文本通过、无限重试或测试程序偷偷恢复来通过验收。

保留原 NodeBB/Navidrome 冻结成绩。修复后重跑 NodeBB 标为“开发回归”，新版本与原版本分别报告；频率调参使用开发样本，正式比较用未参与调参的任务和冻结配置。分别统计协议缺失率、一次补交成功率、故障暂停率、有效用户决策率、恢复正确率及结束能力；任务按时完成与外部 reward 分列。随后按[评测路线](../../evaluation.zh.md)扩大公开任务，再做同 Session 多 Task/Plan/Goal 比较。

上线条件是可恢复、可追踪和任务门禁正确，不能以少调用审查模型代替可靠性。当前只有两个配对样本，不声称 Supervisor 优于 Goal/Plan，也不据此确定最终频率。
