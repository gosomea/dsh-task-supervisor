# Supervisor 整体审查优化提案

## 摘要

本提案让每次审查明确回答：检查哪些原始要求、实际取得哪些证据、哪些结果已确认、为什么等待、下一步由谁执行。先整理审查范围和取证入口，再完善故障处理与要求级裁决，最后统一展示并测量质量与成本。

状态：已批准实施方案，2026-10-09；第一步已实现，后续步骤与发布待完成。本文不表示全部验收完成或新版本已经发布。现有能力见[独立审查](../review-quality.zh.md)和[过程与恢复](../review-experience.zh.md)；本次问题与实际验证见[诊断记录](../postmortem/2026-10-09-review-repair.zh.md)。

## 分析依据

当前已有快照、检查方案、两阶段独立审查、实际读取资格、有限补交和故障恢复。整体优化需要把这些能力连接得更清楚，减少长 Session 中的无关读取与重复判断。

| 观察 | 当前依据 | 需要解决的问题 |
| --- | --- | --- |
| 证据入口默认从 Session 开头查找 | 原始输入读取与事件索引默认从 seq 0 开始，只绑定审查截止点 | 同一 Session 多 Task 时，审查者需要自行辨别本任务范围；这是效率和误归属风险，不代表已经确认误验收 |
| 读取次数不能说明验证覆盖 | 活动统计记录调用、成功读取和错误数量 | 用户仍不知道哪项要求已经检查、哪些仍未确认 |
| 工具失败可能结束审查 | 最新轮次末尾的读取失败记录为故障；协议补交与内部故障重试分别处理 | 可修正的参数问题应有明确修正路径，不能靠完整重跑解决 |
| 原生过程已有展示，但状态有多处计算 | 主对话摘要、DAG 与侧栏分别推导活动状态 | 加载中、重启遗留作业与真实运行需要一致区分；初次加载的旧 pending 作业尚需专门复现验证 |
| 正常任务仍有明显审查成本 | 最近无注入的日志模式任务：计划、节点、完成审查约 53、108、93 秒，成功工具结果共 55 次，失败 4 次 | 数据仅来自一个简单任务，不能推断长期收益；应建立取证成本基线 |

这些数据描述流程可用性和成本，不能证明审查质量或优于 Goal／Plan。现有[机器记录](../postmortem/2026-10-09-review-repair/validation.json)保存各作业耗时和 token 分类。

## Dev Note：优化方案

本节记录已批准设计；实现状态另行记录。实施时更新对应现状文档，验证记录单独保存；运行参数经插件配置校验，安全与证据约束不作为可关闭选项。

### 一、给每场审查一个明确范围

控制器准备可重建的审查输入，绑定 task、要求版本、计划版本、节点尝试、作业、审查 Session、截止点和产物快照。记录当前任务的原始要求、补充约束、授权来源及其事件位置，明确本场要回答的问题。

取证默认优先当前任务、当前节点尝试和本次变化。原始长期约束以及共享产物的相关历史仍可按来源展开；仅按任务创建时间截断会遗漏早先要求，因此不能用简单时间窗口代替归属。无法可靠归属的旧日志标为待核对，不补造历史绑定。

审查输入提供要求来源、适用约束、归一化依赖、必要输入与能力描述。主 Agent 声明必须标明来源；独立发现持久化前，继续隔离主汇报、执行日志和历史裁决。模型可见输入全部写入原生 Session，摘要只帮助定位，不代替原文或实际检查。

| 检查点 | 本场主要问题 | 通过后的含义 |
| --- | --- | --- |
| 规划观察 | 目标是否收敛，未知条件是否减少，是否重复研究，下一项规划产出是什么 | 可以继续规划，不批准实施 |
| 计划审查 | 原始要求是否完整覆盖，依赖是否可执行，必要验证能力是否具备 | 进入既定批准策略，不证明未来交付正确 |
| 进展审查 | 实际工作是否偏移，有无新缺陷、真实卡点或需要修订的计划 | 继续或纠偏，不重复整体验收 |
| 节点审查 | 本次尝试的产物是否满足分配要求，与相关上下游是否兼容 | 释放依赖，不自动接受整体 |
| 整体验收 | 当前完整交付是否满足原始要求，各部分关系是否成立 | 有效裁决应用后完成 Task |

### 二、让证据容易找到，并明确能支持什么

扩展现有索引的任务归属、节点尝试、变化范围和读取范围，优先返回相关调用及配对结果。提供受限批量原文读取，减少“查索引、猜 seq、反复分页”；保留现有 seq 工具兼容。展开必须遵守同一截止点和独立阶段限制。

每份可引用证据关联原事件或产物身份、实际成功读取的范围、截断标记和支持的事实。索引摘要、失败调用、模型自述与工具退出码本身不能证明要求满足；只读到部分内容时，结论也限于该部分。

同一作业内可复用已取得的原始内容与读取资格，记录缓存命中和有效性。跨审查作业的旧结论只作为定位线索；本次必须确认当前产物身份、相关内容与要求是否仍适用。最终验收重新绑定当前快照，不能直接相加节点通过结果。

### 三、先处理可恢复的工具问题，再决定任务是否暂停

工具错误返回稳定错误类型、失败字段、有效范围、可用定位信息和下一步。可修正的读取参数或缺少定位资格，在同一作业内有限纠正；模型实际重读成功后才取得引用资格。裁决校验一次列出缺失要求、无效引用和阶段问题，减少逐个试错。

| 情况 | 拟议处理 | 是否产生执行授权 |
| --- | --- | --- |
| 参数错误、分页错误、尚未定位的引用 | 同一作业给一次明确修正机会，实际读取后重新提交；新发生的相同错误不能无限循环 | 否 |
| 缺少或格式错误的裁决 | 沿用有限协议补交，不延长本次截止时间 | 否 |
| 超时、连接故障、限流、临时服务错误 | 沿用有限内部重试；原身份、快照、阶段与许可仍有效才续行 | 否 |
| 已取得证据表明要求不满足 | 返回具体修订项与影响范围，交主 Agent 修复；完成后重开仍须用户确认 | 否 |
| 必要证据或验证能力缺失 | 保存“未验证”和缺口，给出补证或配置入口；不能给通过结论 | 否 |
| 认证、配置、未知故障或重试耗尽 | 保存现场，明确暂停原因与人工恢复动作 | 否 |
| 用户暂停、关闭、重启或需要用户决定 | 等待手动恢复，旧回调不能继续任务 | 否 |

读取纠正、协议补交和故障重试分别记录，服从已配置的任务截止与各次审查截止。读取纠正次数使用受校验的插件配置，建议默认 1、范围 0–1；补交和读取纠正都不延长当前尝试。权限拒绝、失效快照及独立阶段限制不通过重试绕过。

### 四、按要求保存裁决，明确能力和不确定性

扩展现有要求级发现，在具有明确要求的计划、节点和整体验收中，让日志和独立模式都记录“已满足／未满足／未验证”、检查方法、实际证据、覆盖范围与局限。尚未形成计划的规划观察仍记录事实、未知与下一步；进展观察记录偏移和卡点。日志模式注明经日志核对，独立模式注明实际读取或运行；独立 Session 身份不提供额外验证资格。

审查者从原始要求确定方法：静态内容可读取；计算与行为需要核算、执行或复现；必要观察能力不可用则未验证。既有测试可使用，但须检查断言和实际路径；不得把没有用户依据的优化偏好变成阻断要求。

控制器校验作业身份、证据资格、检查覆盖和裁决格式，模型负责判断证据是否支持事实。格式校验不能保证语义正确，因此验收需要已知缺陷夹具及独立评分。补充发现可修订检查方案，保留此前独立发现，不用对照后的汇报改写它。

续行交接包含本次范围、已确认事项、未完成要求、具体修订、证据位置和下一位执行者。用户看到的是“哪个问题由谁接着处理”，主 Agent 收到的是可执行的交接；控制器仍负责选择就绪节点和准入执行。

### 五、所有展示使用同一份活动状态

统一主对话、DAG 和侧栏的活动解释，分开持久作业结果与运行时事实。加载未知显示“正在读取状态”；只有当前运行实例和事件支持时才显示正在审查。重启遗留作业显示等待恢复，查看历史不投递模型。

主对话保留原生审查过程，折叠摘要显示审查类型、节点、当前动作、实测耗时及下一步。正在运行、自动恢复、故障和等待用户都有明显文字与主题颜色；不要只依赖小圆点。用户主动收起的选择继续保留。

DAG 显示节点与尝试进度，侧栏展开要求、证据、覆盖局限及历史。要求覆盖可以显示“3 项中已核对 2 项，1 项未验证”，但需标明来源和总数，不能伪装为任务完成百分比。当前活动与上次裁决明确分开。

### 实施顺序与验收

| 顺序 | 交付范围 | 必须通过的验收 |
| --- | --- | --- |
| 1：范围与状态 | 审查输入归属、相关证据优先定位、统一活动解释、现状文档整合 | 同一 Session 多 Task 和早先长期约束正确归属；无关历史不变成要求；冷加载与重启不会误报运行 |
| 2：取证与纠错 | 原文批量读取、实际范围引用、明确工具错误、有限读取修正 | 错误参数可修正；摘要及失败读取仍拒绝引用；暂停能取消修正；补交不延长截止；两阶段隔离不泄漏 |
| 3：裁决与交接 | 日志与独立模式的要求级结果、最终组合检查、具体续行交接、覆盖展示 | 静态文档、数据计算、行为遗漏、误导汇报和能力缺失均有正反例；正确产物不被无关偏好阻塞 |
| 4：长程验证与发布 | 同配置冻结对照、成本报告、普通安装验证、发布证据 | 两种模式、同 Session 多 Task、返工、超时、重启、产物变化及历史订阅释放均验证；公开包与验收产物一致 |

每步完成针对性内核、原生 Host 与用户可见快照检查，更新中英文文档，单独 commit、push。涉及客户端时执行双端严格类型检查、构建和打包；真实模型验收复用登记隔离环境及当天模型路由，不重启日常 3080 的在途任务。

先建立当前版本基线，再以相同 Host、profile、模型、输入、批准策略和截止对比候选版本。固定首轮审查频率，记录成功与失败位置，不向暂停任务追加救场；已分析题只作开发回归，公开题沿用现有冻结与独立评分协议。

硬性门槛：已知错误夹具不得误通过，正确夹具不得因附加偏好被拒绝，用户暂停后不得自动续行，旧产物不得接受新裁决，同一作业不得重复应用或启动。确定性行为用受控模型与时钟验证；真实模型结果保留重复试验和不确定性。

同时记录最终成功／独立奖励、要求与独立检查覆盖、工具故障、恢复次数、重复读取、各阶段耗时、主与全部审查 Session token、用户操作次数。误验收与误暂停需要人工或盲审标签；没有标签保持 null。将验证质量与恢复成功率分别报告，减少读取和耗时必须同时检查覆盖是否下降。

本轮能力范围为现有产物读取、隔离命令运行、公开 Session 和原生对话组件。独立浏览器及视觉执行器仍属后续能力扩展；所需能力缺失明确展示。完成以上验证后再确定 patch 版本、冻结 tarball、普通安装验收和发布，不预先宣称性能改善或优于 Goal／Plan。

## 已批准的交付顺序

1. 原生 Markdown 完整持久报告、独立过程折叠，以及统一活动和应用解释。

2. 持久任务／尝试／变化范围、筛选索引与原始证据批量读取，同作业一次读取纠正。

3. 要求级结果和具体交接，审查记录版本 8，继续读取版本 1–7。

4. 受控回归、登记环境真实模型与浏览器、冻结同配置对照、干净安装及下一可用 patch 发布。

每步更新中英文现状与证据后单独提交推送。日常 3080 保持运行。审查频率不变；没有盲审标注时误验收与误暂停指标保持 null。
